What is an agent?

A model in a ReAct loop (reason, act, observe), plus the knowledge it reads, the tools it calls, the skills it loads and the harness that runs it all.

The model only suggests. The harness acts, as a process, with your access.

Where should the guardrail live?

Same picture, three places: in the prompt, inside the harness, or outside the whole process.

Only the outside can't be argued with or bypassed from within.

Enter NVIDIA OpenShell

One tool for building that boundary: an open-source runtime that puts the whole agent process in a sandbox governed by a YAML policy.

You declare what the agent can touch. OpenShell enforces it from outside.

Same agent, inside OpenShell

Same picture, same poisoned issue. The model is still misled, but every harmful step now stops at the boundary.

OpenShell doesn't make the agent smarter. It makes its mistakes harmless.

The big picture

A gateway (control plane) and, per sandbox, a trusted supervisor beside an untrusted workload (data plane), built around an agent as it runs on Kubernetes.

The gateway never decides a packet. The supervisor decides every one.

The boundary up close

openshell-sandbox lives inside with the agent. It owns the process tree, names the calling binary and holds nothing worth stealing.

openshell-supervisor lives outside. It holds policy, credentials and DNS, and opens every real connection.

One mTLS HTTP/2 connection between them, one stream per TCP connection.

The supervisor moved out

In 0.0.x the supervisor ran inside the agent's container as its parent, with the privilege to build the boundary right next to the agent.

0.1.0 (RFC 0012) split it: a capability-free runtime inside, the supervisor outside, an isolation-backend contract between.

0.0.x sandboxes can't be upgraded in place. Recreate them.

One YAML file, two lifetimes

This is the policy for a coding agent. Each step highlights one section and explains it.

Startup sections lock when the sandbox starts. Live sections change while it runs.

version: 1
filesystem_policy:          # startup
  include_workdir: true
  read_only: [/usr, /lib, /etc, /proc]
  read_write: [/tmp]
landlock:                   # startup
  compatibility: hard_requirement
process:                    # startup
  run_as_user: sandbox
  run_as_group: sandbox
network_policies:           # live
  github:
    endpoints:
      - host: api.github.com
        port: 443
        protocol: rest
        enforcement: enforce
        access: read-only
    binaries:
      - path: /usr/bin/gh
  pypi:
    endpoints:
      - { host: pypi.org, port: 443 }
      - { host: files.pythonhosted.org, port: 443 }
    binaries:
      - path: /usr/bin/python3.12
network_middlewares:        # live
  redact-secrets:
    middleware: openshell/regex
    config: { mode: redact }
    endpoints:
      include: ["api.github.com"]
A policy for a coding agent

One YAML file with five sections. The first three build the walls when the sandbox starts. The last two decide traffic, and you can change them while the agent runs.

startup filesystem_policy, landlock, processlive network_policies, network_middlewares

Press → to walk through it, one section at a time.

1filesystem_policy
Enforced by Landlock, in the kernelTakes effect at startup

Lists the paths the agent can read, or read and write. Everything else is inaccessible. include_workdir adds the working directory, here the cloned repo under /sandbox.

Paths must be absolute, without .., at most 256 of them, and read_write can't be /. With any network rule, OpenShell also adds baseline read paths such as /usr and /etc.

For this agent: it can edit the repo and /tmp. ~/.ssh isn't listed, so the injected cat ~/.ssh/id_ed25519 gets EACCES.
2landlock
Enforced by openshell-sandboxTakes effect at startup

compatibility decides what happens if Landlock can't apply your filesystem rules. Both modes need a kernel with Landlock ABI v3 or later, and both skip individual paths that don't exist.

best_effort (default)Runs without the filesystem rules and logs a high-severity finding.
hard_requirementRefuses to start.
For this agent: hard_requirement. An agent holding your repo and tokens should never run unconfined.
3process
Applied by the compute driverTakes effect at creation

run_as_user and run_as_group: sandbox or a numeric ID from 1 to 4294967294, so root is rejected. Docker and Podman apply them at creation; Kubernetes uses its driver's identity. Policy updates can't change them.

Not in the file, but always on: no Linux capabilities, no_new_privs, and seccomp filters that block escalation and escape syscalls.

For this agent: it runs as sandbox, so the injected sudo and mount get EPERM.
4network_policies
Enforced by the supervisor's proxyTakes effect live

A map of named rules. Each rule pairs endpoints with binaries; a connection is allowed only when both match. Anything not listed is denied.

protocol: rest turns on request inspection. enforcement: enforce makes request rules block; the default, audit, only logs. access: read-only allows GET, HEAD and OPTIONS.

For this agent: gh can read GitHub and python3.12 can reach PyPI. curl matches no rule, so the upload to paste.example is denied, and DELETE on the repo gets 403.
5network_middlewares
Enforced by the supervisor, on allowed trafficTakes effect live

Up to 10 configurations that run, in ascending order, on traffic the rules allow and before credentials are added. Use the built-in openshell/regex or your own service registered with the gateway.

on_error defaults to fail_closed: if the middleware fails, the request is blocked.

For this agent: anything secret-looking in a request to GitHub is redacted before it leaves.
Two lifetimes
startup recreate the sandbox to changelive hot-reloaded while it runs

A live change goes to the gateway, which validates it and saves a new revision. The supervisor validates it again, then loads it. Connections opened under the old rules close.

openshell policy set issue-142 --policy agent.yaml --wait
openshell policy get issue-142 --base

Startup sections can't change in place: adding a path is saved but not applied, and removing one is rejected.

Which policy runs
1. Global policyReplaces every sandbox's policy and blocks edits
2. Saved sandbox policyFrom --policy at create, or policy set
3. Image policyA policy baked into the image
4. DefaultRestrictive, with no network

Attached providers then add their own endpoints: base policy + provider rules = effective policy. That is what the supervisor enforces.

If loading fails, fail_closed (the default) blocks traffic; retain_last_valid keeps the old policy.

The agent never holds the key

Providers keep credentials in the gateway. Inside the sandbox the agent sees only placeholders such as openshell:resolve:env:GITHUB_TOKEN.

The supervisor swaps in the real value only for endpoints the provider allows.

Steal the environment and you get placeholders.

Two kernel filters

seccomp decides which system calls a process may make. Landlock decides which files and folders it may touch.

openshell-sandbox switches both on before the agent starts; every process the agent starts inherits them.

They run in whichever kernel runs the agent.

Three signals, one sandbox ID

Traces show where time goes, gateway metrics show saturation, and OCSF events record every security decision.

Supervisors export directly. Agent spans go to a relay at 192.0.0.8:4318, with no egress rule needed.

Reading an OCSF event

OpenShell maps security events to OCSF v1.8.0: network and HTTP decisions, processes, SSH, authentication, config changes and findings.

The same event appears as a shorthand line, a JSONL record or an OTLP log record.

OTLP delivery is at least once. Deduplicate on ocsf.metadata.uid and alert on gaps.

Anatomy of a shorthand line

OCSFevent NET:OPENclass:activity [MED]severity DENIEDaction /usr/bin/curl(64) -> httpbin.org:443process(pid) -> destination [policy:- engine:opa]which rule decided [reason:no matching policy]context

Event classes

NET: Network Activity 4001 HTTP: HTTP Activity 4002 SSH: SSH Activity 4007 PROC: Process Activity 1007 FINDING: Detection Finding 2004 AUTH: Authentication 3002 API: API Activity 6003 CONFIG: Device Config State Change 5019 LIFECYCLE: Application Lifecycle 6002 EVENT Base Event 0

One event, three forms

  • Shorthand, always on: gateway console, openshell logs, the TUI and the supervisor log file
  • JSONL, full record: [openshell.gateway.ocsf_log] for the gateway; the ocsf_json_enabled setting for supervisors
  • OTLP logs, off by default: [openshell.gateway.otlp.ocsf] enabled = true; supervisors export directly

As an OTLP log record

  • Body: the OCSF event as JSON; scope openshell.ocsf
  • Severity: Low is WARN, Medium WARN2, High ERROR, Critical ERROR2
  • Attributes: ocsf.class_uid, ocsf.activity_id, ocsf.severity_id, ocsf.metadata.uid, openshell.sandbox.id

Delivery guarantees

Up to 4 attempts with backoff, so delivery is at least once: deduplicate on ocsf.metadata.uid. The queue holds 10,000 records or 16 MiB, and batches go at 100 records, 1 MiB or 500 ms. Drops are counted in openshell_ocsf_otlp_dropped_total{reason}, and the next batch carries an openshell.ocsf.gap record with the count. Treat OCSF as best-effort evidence, not a complete audit history.

One sandbox on Kubernetes

Built up in deployment order: LiteLLM, observability, OpenShell, a workspace, then a sandbox.

The agent reaches its model only through the supervisor and LiteLLM.

Dedicated or shared?

By default every sandbox gets its own supervisor Pod. With supervisor_topology: gateway, a shared Deployment hosts many.

Either way, each sandbox keeps its own policy, identity and gateway session.

Shared saves Pods but widens the blast radius. Failover keeps processes, not connections.

An HA control plane

Run 2+ gateway replicas as a Deployment on PostgreSQL. Each supervisor keeps one session to one replica, which records ownership.

Other replicas relay to the owner through a headless peer Service.

Scale on CPU. New replicas don't take existing sessions.

Connect Keycloak and SPIFFE

Keycloak identifies people: the CLI, SDKs and portal sign in with OIDC. SPIFFE identifies workloads: each sandbox gets a short-lived identity to trade for upstream tokens.

No long-lived secrets: people carry tokens, sandboxes carry SVIDs.
