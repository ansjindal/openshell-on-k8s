You just watched the fleet investigate. There's no magic in it: it's a small orchestrator in this very website (`training/src/app/api/orchestrate/route.ts`, about 150 lines). This page shows you **all of it**: the plan, the exact prompt each agent gets, how a sealed agent is invoked, and how the analyst concludes.

<FleetOrchestration />

<Part n="1">A fixed plan, no model call to "plan"</Part>

Many "agent orchestrators" spend a model call just to decide what to do. This one doesn't. The plan is **fixed**: one step per specialist, and each step names the **tool call** that specialist should make. The intelligence is in each agent making the call and interpreting the result, and in the analyst's synthesis, all through the agents' own governed model access, never from the website:

```ts
const PROBES = {
  metrics: { call: `prometheus_query("sum by (code) (rate(shop_requests_total{namespace=\"demo\"}[2m]))")
                    and prometheus_query("kube_deployment_status_replicas_available{namespace=\"demo\"}")`,
             hint: "the shop's request rate by HTTP code (5xx is the error rate) and each Deployment's available replicas" },
  logs:    { call: `loki_query("{namespace=\"demo\", app=\"shop-app\"} |= \"error\"", 30)`,
             hint: "the shop's recent error lines: what failed and which dependency" },
  events:  { call: `cluster_events("demo") and pod_status("demo")`,
             hint: "what Kubernetes changed recently and which pods are missing or not ready" },
  traces:  { call: `tempo_search("{ resource.service.name = \"shop\" && status = error }", 30)`,
             hint: "recent error traces of the shop: how many, which operation, how long" },
};
```

The `call` is also what the incident page shows under each agent, so you see what it's doing, not a spinner.

<Part n="2">Each agent gets a directive sub-task</Part>

A small model given a vague task wanders: it lists tools, tries several, and runs long. So each specialist's prompt names its call and what to return:

```ts
const subtask =
  `Incident: ${task}

   Investigate it in your role. Call your sre-tools tool exactly like this: ${p.call}.
   It returns ${p.hint}. Then report at most five bullets of concrete findings, each naming
   the tool and the values it returned, and STOP. No proposals, no greeting.`;
```

Its role (`/sandbox/ROLE.md`) and the platform skills do the rest: what to ignore, how to read the numbers. If a model still reaches for a tool it isn't allowed, its supervisor refuses the call: the policy, not the prompt, is the boundary.

<Part n="3">How a sealed agent is invoked</Part>

Each step runs **inside the agent's sandbox**, through the `pi` that ships in the sandbox image (already pointed at LiteLLM, so no `--provider` or `--model`). The website runs `openshell sandbox exec`; the prompt goes base64-encoded, because `exec` rejects arguments with newlines:

```ts
const PI = "pi --no-session --append-system-prompt /sandbox/ROLE.md";

openshell(["sandbox", "exec", "-n", agent, "--", "sh", "-c",
  `${PI} -p "$(printf %s ${b64} | base64 -d)"`]);
```

So every model call goes through the agent's `litellm` provider (the supervisor adds the key), and every tool call goes through its `sre_tools` rule. The website holds no model key and no tool access: it can only ask the agents.

<Part n="4">The analyst concludes</Part>

The specialists run in **parallel**. When they're all in, their findings go to the **analyst**, run with `--no-mcp --no-tools`, which reasons over them into a root cause and a recommended action:

```ts
const analystPrompt =
 `You are the incident analyst synthesizing an SRE fleet's findings. Reason ONLY over the
  findings below: do NOT use any tool, and do NOT greet, ask questions, or describe yourself.
  Begin your reply directly with "ROOT CAUSE:". … ask "what changed?" … Then, on a FINAL
  separate line, output exactly:
  RECOMMENDED_ACTION: <the specific reversal>`;
```

The whole run is streamed to the page as newline-delimited JSON (`plan` → `step start/done` → `writer` → `answer`), which is why you see the live timeline, each agent's call, and its findings as they happen.

<Callout type="rh" title="Why it's built this way">
Two honest constraints shaped this: a small model can't hold a free-form investigation over large telemetry (so each specialist gets one prescribed call), and agents must not hold credentials to the systems they read (so the tools live in an MCP server, and each agent's policy names the ones it may call). The result is <strong>reliable and real</strong>: every agent queries live cluster state through a governed tool, and the analyst's recommendation comes from that evidence. Read it, change it, own it.
</Callout>
