In [0.4](/learn/agent-on-k8s) you ran pi as an ordinary pod: it reached any host, held the real LiteLLM key and could talk to the Kubernetes API. Now bring up the **same agent** as a sandboxed agent, from the ground up: a workspace of your own, its model provider, the sandbox, then pi inside it, with exactly one door opened so pi can be installed.

**Concept:** [Parts 2 and 3 in the Overview](/learn/openshell#t-2): the same agent inside OpenShell, and how OpenShell is built.

<Section n="1" title="Create a workspace for your agent">

A **workspace** is OpenShell's tenant: its own sandboxes, providers and members. On this cluster each workspace is a Kubernetes **namespace of the same name**: the gateway runs in *operator mode*, so it doesn't create namespaces; you prepare one, and the gateway uses it. The platform's own workspace, `lab` (where `agent-0` runs), was made this way at setup. Now make yours, `dev`.

<Step n="1" title="Create the namespace and label it as a workspace">

The gateway watches for namespaces labelled `openshell.ai/workspace=true` (its `operatorNamespaceLabel` setting). `--dry-run=client -o yaml | kubectl apply` makes this safe to run twice:

```bash
kubectl create namespace dev --dry-run=client -o yaml | kubectl apply -f - && kubectl label namespace dev openshell.ai/workspace=true --overwrite
```
<Output>
<ExpectedOutput>
{`namespace/dev created
namespace/dev labeled`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Install the openshell-workspace chart into it">

NVIDIA's **`openshell-workspace`** Helm chart, the same version as the gateway, puts what sandboxes need into the namespace:

```bash
helm upgrade --install openshell-workspace oci://ghcr.io/nvidia/openshell/openshell-workspace --version 0.1.7 --namespace dev --wait
```
<Output summary="One Helm release in dev.">
<ExpectedOutput>
{`Release "openshell-workspace" does not exist. Installing it now.
NAME: openshell-workspace
NAMESPACE: dev
STATUS: deployed
REVISION: 1`}
</ExpectedOutput>
</Output>

List what it made:

```bash
kubectl -n dev get serviceaccount,role,rolebinding,networkpolicy
```
<Output>
<ExpectedOutput>
{`NAME                               AGE
serviceaccount/default             2s
serviceaccount/openshell-sandbox   0s

NAME                                                         CREATED AT

</ExpectedOutput>

- **`openshell-sandbox`**: the ServiceAccount sandbox pods run as. It has no Kubernetes permissions of its own.
- **Role and RoleBinding `openshell-workspace-sandbox`**: let the **gateway's** ServiceAccount (in `openshell`) create and manage `Sandbox` resources, pods and Secrets in **this** namespace only.
- **NetworkPolicy `openshell-workspace-sandbox-ssh`**: only the gateway's pods may reach sandboxes for `exec` and `connect`.

</Step>

<Step n="3" title="Create the workspace in the gateway">

The namespace is ready; now tell the gateway about it. The workspace name is the namespace name:

```bash
openshell workspace create --name dev && openshell workspace list
```
<Output>
<ExpectedOutput>
{`✓ Created workspace dev
NAME     STATUS        CREATED               LABELS
default  Active        2026-11-11 11:41:33
lab      Active        2026-11-13 10:31:49
dev      Active        2026-11-13 10:33:06`}
</ExpectedOutput>
</Output>

From now on, `--workspace dev` on an `openshell` command acts on your workspace. Without it, commands act on `lab`, the default set for this shell (`OPENSHELL_WORKSPACE=lab`).

</Step>

<Step n="4" title="Give the workspace the litellm provider">

Providers belong to a workspace, so `dev` has none yet. Create one exactly the way the platform created `lab`'s ([1.3](/learn/inference)): LiteLLM's key goes from its Secret into the `LITELLM_API_KEY` variable of this one command, and `--credential LITELLM_API_KEY` reads it from there, so it is never printed:

```bash
LITELLM_API_KEY="$(kubectl -n litellm get secret litellm-secrets -o jsonpath='{.data.LITELLM_MASTER_KEY}' | base64 -d)" openshell --workspace dev provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY && openshell --workspace dev provider list
```
<Output>
<ExpectedOutput>
{`✓ Created provider litellm
NAME     TYPE     CREDENTIAL_KEYS   CONFIG_KEYS
litellm  litellm  1                 0`}
</ExpectedOutput>
</Output>

</Step>

<Section n="2" title="Create the sandbox with openshell sandbox create">

You don't write Kubernetes objects for a sandbox: you ask the **gateway** for one with the `openshell` CLI, and it does the rest.

<Step n="1" title="Read the create command, flag by flag, and run it">

| Part | What it does |
|---|---|
| `openshell sandbox create` | Asks the gateway for a new sandbox. The CLI talks only to the gateway (with the lab operator's certificate), never to Kubernetes. |
| `--workspace dev` | Which workspace the sandbox belongs to, so which namespace it runs in: `dev`. |
| `--name pi-agent` | The sandbox's name: you use it in every later command (`exec`, `policy`, `logs`, `delete`). |
| `--provider litellm` | Attaches the workspace's `litellm` provider (step 1.4.1.4): the sandbox gets a placeholder `LITELLM_API_KEY`, and the provider's rule for LiteLLM is merged into its policy. |
| `--policy manifests/policies/baseline.yaml` | The policy it starts with: the lab's baseline, which lets the agent write only `/sandbox` and `/tmp` and opens **no network at all**. |
| `--memory 2Gi` | The workload pod's memory request and limit. (`--cpu` would become a request too; on an 8-vCPU VM a few of those fill the node.) |
| `--no-tty --detach` | Don't attach a terminal, and return as soon as the sandbox is requested. |
| `-- sleep infinity` | Everything after `--` is the sandbox's **main process**. The sandbox lives as long as it runs; `sleep infinity` keeps it up so you can `exec` into it. |
| (no `--from`) | The gateway's default image, `ghcr.io/ansjindal/openshell-on-k8s/pi-sandbox`: Node, npm, Python, curl and git on the OpenShell base, plus a ready-made pi (used from Module 2 on). Here you install pi yourself, as in 0.4, to see the policy at work. |

```bash
cd ~/openshell-on-k8s && openshell --workspace dev sandbox create --name pi-agent --provider litellm --policy manifests/policies/baseline.yaml --memory 2Gi --no-tty --detach -- sleep infinity
```
<Output summary="The gateway accepts the request and starts creating the sandbox.">
<ExpectedOutput>
{`Created sandbox: pi-agent

  [0.0s] Requesting compute...`}
</ExpectedOutput>
</Output>

Without `--detach` and a trailing command, `openshell --workspace dev sandbox create` opens an interactive shell in the new sandbox instead; type `exit` to leave.

</Step>

<Step n="2" title="Wait until it is Ready">

**`openshell --workspace dev sandbox list`** shows every sandbox in your workspace and its phase. Give it a few seconds:

```bash

```
<Output summary="pi-agent is Ready, the only sandbox in dev.">
<ExpectedOutput>
{`NAME      CREATED              PHASE
pi-agent  2026-11-13 10:33:06  Ready`}

<Section n="3" title="See what the gateway made on the cluster">

For that one command, the gateway:

1. stored the sandbox and its policy (revision 1);
2. wrote a `Sandbox` resource in the workspace's namespace, `dev`, which the **agent-sandbox controller** turned into the **workload pod** `pi-agent`, where the agent runs;
3. started the **supervisor pod** `os-supervisor-<id>`, which fetched the policy and the provider's credential and became the workload's only way out.

<Step n="1" title="List the Sandbox resources">

`Sandbox` is a custom resource (`agents.x-k8s.io`), so `kubectl` can list it like any other object:

```bash
kubectl -n dev get sandboxes
```
<Output>
<ExpectedOutput>
{`NAME       READY   REASON              AGE
pi-agent   True    DependenciesReady   13s`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="See each pod's role and its pair">

Each sandbox is **two pods**. Their labels say which is which: `boundary-role` is `workload` or `supervisor`, and `boundary-pair` is the sandbox's id, shared by the two. `-L` shows those labels as columns:

```bash
kubectl -n dev get pods -L openshell.ai/boundary-role,openshell.ai/boundary-pair
```

<ExpectedOutput>
{`NAME                                                 READY   STATUS    AGE   BOUNDARY-ROLE   BOUNDARY-PAIR
os-supervisor-64aee23c-9946-4c69-b500-c39ec1b03a7d   1/1     Running   13s   supervisor      64aee23c-9946-4c69-b500-c39ec1b03a7d

</ExpectedOutput>

`openshell --workspace dev sandbox get pi-agent` shows the same sandbox from the gateway's side: its id, phase and runtime.

<Step n="3" title="The NetworkPolicy that pairs them">

The isolation between the two pods is ordinary Kubernetes **NetworkPolicy**: the gateway made three with the sandbox, next to the chart's SSH policy:


<ExpectedOutput>

<Section n="4" title="Test the seal from inside">

The agent runs as the unprivileged user `sandbox`. Before it starts, the sandbox runtime applies the policy's static parts:

- **Landlock** (a Linux security module) limits the filesystem: `/usr`, `/lib`, `/etc` read-only, `/sandbox` and `/tmp` writable, everything else invisible. OpenShell 0.1 needs Landlock ABI v3, so the node needs Linux 6.2 or newer.
- **seccomp** filters dangerous system calls, and the process can't regain root.
- These are **static**: fixed when the sandbox is created.

<ReadScene scene="kernel" />

Kubernetes adds two guardrails of its own: a sandbox may use a cluster resource (a RuntimeClass, a PriorityClass, a volume) only if the operator labelled it `openshell.ai/sandbox-attachable=true`, and **Kyverno** rejects any sandbox pod that asks for the host's network, PID or IPC namespace.

Now check it. **`openshell --workspace dev sandbox exec -n pi-agent -- <command>`** runs one command inside the sandbox, through the gateway and the supervisor, and returns.

<Step n="1" title="Who the agent runs as">

```bash
openshell --workspace dev sandbox exec -n pi-agent -- id
```
<Output summary="An unprivileged user, not root.">
<ExpectedOutput>
{`uid=10001 gid=10001 groups=10001`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="The filesystem, enforced by Landlock">

Try to write in `/usr`, write in `/sandbox`, and list `/root`:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'touch /usr/x; touch /sandbox/x && echo "/sandbox is writable"; ls /root'
```
<Output>
<ExpectedOutput>
{`touch: cannot touch '/usr/x': Permission denied
/sandbox is writable
ls: cannot open directory '/root': Permission denied`}
</ExpectedOutput>
</Output>

Exactly the policy's `filesystem_policy`.

</Step>

<Step n="3" title="The Kubernetes API is out of reach">

In 0.4 the agent's pod reached the API server with its ServiceAccount token. Here `curl` gets no connection at all (`-m 6` gives up after six seconds; exit 7 means it couldn't connect):

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'curl -sk -m 6 -o /dev/null https://kubernetes.default.svc.cluster.local/version || echo "blocked (curl exit $?)"'
```
<Output>
<ExpectedOutput>

</ExpectedOutput>
</Output>

</Step>

<Section n="5" title="Install pi: refused, then one door opened">

<Step n="1" title="Ask npm for pi">

The sandbox image has Node and npm. Ask the npm registry for pi's latest version (`--fetch-retries=0 --fetch-timeout=5000` makes it fail fast instead of retrying):

```bash
openshell --workspace dev sandbox exec -n pi-agent -- npm view @earendil-works/pi-coding-agent version --fetch-retries=0 --fetch-timeout=5000
```
<Output summary="Refused: connect EACCES. The connection never left the sandbox.">
<ExpectedOutput>
{`npm error code EACCES
npm error syscall connect
npm error errno EACCES
npm error FetchError: request to https://registry.npmjs.org/@earendil-works%2fpi-coding-agent failed, reason: connect EACCES 198.18.0.2:443 - Local (0.0.0.0:0)
...`}
</ExpectedOutput>
</Output>

The supervisor wrote down why. **`openshell --workspace dev logs pi-agent`** prints the sandbox's log; its `OCSF` lines are the audit events:

```bash
openshell --workspace dev logs pi-agent | grep OCSF | grep registry.npmjs.org | tail -1
```
<Output summary="One OCSF event: node tried registry.npmjs.org:443, and no policy allows it.">
<ExpectedOutput>
{`[1794566012.787] [sandbox] [OCSF ] [ocsf] NET:OPEN [MED] DENIED /usr/bin/node(0) -> registry.npmjs.org:443 [reason:transparent_tcp_policy_denied]`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="The policy file, then one door">

Every layer of a sandbox is set by one short YAML file: its **policy**. The baseline you created `pi-agent` with is one; here it is line by line, with what each part lets through and what it stops:

<ReadScene scene="policy" />

| Part | Controls | Enforced by | Changes on a running sandbox? |
|---|---|---|---|
| `filesystem_policy` | paths readable / writable | Landlock, in the kernel | no, fixed at creation |
| `landlock` | how strict if the kernel lacks a Landlock feature | the sandbox runtime | no |
| `process` | the user and group the agent runs as | the sandbox runtime | no |
| `network_policies` | hosts, ports, methods, paths, programs | the supervisor | **yes**: `openshell policy set` / `policy update` |

`manifests/policies/pi-agent.yaml` is the baseline plus one grant: the npm registry, **read-only**, for **`/usr/bin/node` only**.

<YamlRead id="pi-agent-policy" />

**`openshell --workspace dev policy set`** replaces the sandbox's policy with a file; `--wait` returns once the supervisor has loaded it:

```bash
cd ~/openshell-on-k8s && openshell --workspace dev policy set pi-agent --policy manifests/policies/pi-agent.yaml --wait
```
<Output summary="Revision 2 is loaded into the running sandbox: no restart.">
<ExpectedOutput>
{`✓ Policy version 2 submitted (hash: 6750e23ab498)
✓ Policy version 2 loaded (active version: 2)`}
</ExpectedOutput>
</Output>

</Step>

<Section n="6" title="Run pi sealed: the model works, nothing else does">

<Step n="1" title="Point pi at LiteLLM, with the placeholder">

The same `models.json` as in 0.4: LiteLLM's address, and `apiKey: "$LITELLM_API_KEY"`, a reference pi resolves from its environment. Here that variable holds the placeholder:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'mkdir -p ~/.pi/agent && cat > ~/.pi/agent/models.json <<EOF

      "baseUrl": "http://litellm.litellm.svc.cluster.local:4000/v1",
      "api": "openai-completions",

      "compat": { "supportsDeveloperRole": false, "supportsReasoningEffort": false },

  }
}
EOF
grep apiKey ~/.pi/agent/models.json'
```

<Optional title="The same agent, two places">

| | 0.4: an ordinary pod | 1.4: an OpenShell sandbox |
|---|---|---|
| Model key | the real key in its environment | a placeholder; the supervisor adds the key on allowed calls |
| Network | any host, and the Kubernetes API | only what the policy allows, per binary, method and path |
| Files | the whole container | `/sandbox` and `/tmp` writable, system paths read-only, the rest invisible |
| Audit | nothing in the pod's log | every allow and deny as an OCSF event |
| Changing it | edit the Deployment, restart | `openshell policy set` on the running sandbox |

</Optional>

<Callout type="lab" title="A sandbox is a pair of pods plus a policy">
No magic VM: a workload pod with a locked-down process, a supervisor pod that owns its network, and NetworkPolicy between them. Kubernetes gives you scheduling, lifecycle and RBAC; OpenShell adds the isolation, the policy and the audit trail on top.
</Callout>

## What you learned

<Learned next="/learn/policy" nextLabel="Open its network, rule by rule">

- **`openshell sandbox create` asks the gateway**, which writes a Sandbox resource and starts a supervisor pod; the controller makes the workload pod.
- **The seal holds from inside.** An unprivileged user, Landlock on the filesystem, no route to the Kubernetes API, and a placeholder instead of the key.
- **The network is deny by default.** npm and curl were refused, and each refusal is in the audit log.
- **A policy opens one door at a time.** One read-only rule, for one binary, applied to the running sandbox.

</Learned>
