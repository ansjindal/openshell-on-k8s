In [0.4](/learn/agent-on-k8s) you ran pi as an ordinary pod: it reached any host, held the real LiteLLM key and could talk to the Kubernetes API. Now bring up the **same agent** as a sandboxed agent, in the workspace `dev` you made in [1.3](/learn/inference) and with the `litellm` provider you added there: the sandbox first, then pi inside it, sealed.

**Concept:** [Parts 2 and 3 in the Overview](/learn/openshell#t-2): the same agent inside OpenShell, and how OpenShell is built.

<Section n="1" title="Create the sandbox with openshell sandbox create">

You don't write Kubernetes objects for a sandbox: you ask the **gateway** for one with the `openshell` CLI, and it does the rest.

<Diagram id="sandbox-create" n="1.6" caption="One command, three results: the gateway stores the sandbox and its policy, writes a Sandbox resource that the controller turns into the workload pod, and starts the supervisor pod that becomes its only way out." />

<Step n="1" title="Read the create command, flag by flag, and run it">

| Part | What it does |
|---|---|
| `openshell sandbox create` | Asks the gateway for a new sandbox. The CLI talks only to the gateway (with the lab operator's certificate), never to Kubernetes. |
| `--workspace dev` | Which workspace the sandbox belongs to, so which namespace it runs in: `dev`. |
| `--name pi-agent` | The sandbox's name: you use it in every later command (`exec`, `policy`, `logs`, `delete`). |
| `--provider litellm` | Attaches the `litellm` provider you added to `dev` in [1.3](/learn/inference): the sandbox gets a placeholder `LITELLM_API_KEY`, and the provider's rule for LiteLLM is merged into its policy. |
| `--policy manifests/policies/baseline.yaml` | The policy it starts with: the lab's baseline, which lets the agent write only `/sandbox` and `/tmp` and opens **no network at all**. |
| `--memory 2Gi` | The workload pod's memory request and limit. (`--cpu` would become a request too; on an 8-vCPU VM a few of those fill the node.) |
| `--no-tty --detach` | Don't attach a terminal, and return as soon as the sandbox is requested. |
| `-- sleep infinity` | Everything after `--` is the sandbox's **main process**. The sandbox lives as long as it runs; `sleep infinity` keeps it up so you can `exec` into it. |
| (no `--from`) | The gateway's default image, `ghcr.io/ansjindal/openshell-on-k8s/pi-sandbox`: Node, npm, Python, curl and git on the OpenShell base, plus pi, ready to run (Section 4). |

```bash
cd ~/openshell-on-k8s && openshell --workspace dev sandbox create --name pi-agent --provider litellm --policy manifests/policies/baseline.yaml --memory 2Gi --no-tty --detach -- sleep infinity
```
<Output summary="The gateway accepts the request and starts creating the sandbox.">
<ExpectedOutput>
{`Created sandbox: pi-agent

  [0.0s] Requesting compute...`}
</ExpectedOutput>
</Output>

Without `--detach` and a trailing command, `openshell --workspace dev sandbox create` opens an interactive shell in the new sandbox instead; type `exit` to leave.

</Step>

<Step n="2" title="Wait until it is Ready">

**`openshell --workspace dev sandbox list`** shows every sandbox in your workspace and its phase. Give it a few seconds:

```bash
openshell --workspace dev sandbox list
```
<Output summary="pi-agent is Ready, the only sandbox in dev.">
<ExpectedOutput>
{`NAME      CREATED              PHASE
pi-agent  2026-11-13 10:33:06  Ready`}
</ExpectedOutput>
</Output>

</Step>

<Section n="2" title="See what the gateway made on the cluster">

For that one command, the gateway:

1. stored the sandbox and its policy (revision 1);
2. wrote a `Sandbox` resource in the workspace's namespace, `dev`, which the **agent-sandbox controller** turned into the **workload pod** `pi-agent`, where the agent runs;
3. started the **supervisor pod** `os-supervisor-<id>`, which fetched the policy and the provider's credential and became the workload's only way out.

<Diagram id="sandbox-pair" n="1.7" caption="The two pods share a pair id. The NetworkPolicies the gateway made let the workload talk only to its own supervisor, and the supervisor lets out only what the policy allows." />

<Step n="1" title="List the Sandbox resources in dev">

`Sandbox` is a custom resource (`agents.x-k8s.io`), so `kubectl` can list it like any other object:

```bash
kubectl -n dev get sandboxes
```
<Output>
<ExpectedOutput>
{`NAME       READY   REASON              AGE
pi-agent   True    DependenciesReady   13s`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="See each pod's role and its pair">

Each sandbox is **two pods**. Their labels say which is which: `boundary-role` is `workload` or `supervisor`, and `boundary-pair` is the sandbox's id, shared by the two. `-L` shows those labels as columns:

```bash
kubectl -n dev get pods -L openshell.ai/boundary-role,openshell.ai/boundary-pair
```
<Output summary="pi-agent and os-supervisor-64aee23c…: one pair, one id.">
<ExpectedOutput>
{`NAME                                                 READY   STATUS    AGE   BOUNDARY-ROLE   BOUNDARY-PAIR
os-supervisor-64aee23c-9946-4c69-b500-c39ec1b03a7d   1/1     Running   13s   supervisor      64aee23c-9946-4c69-b500-c39ec1b03a7d
pi-agent                                             1/1     Running   13s   workload        64aee23c-9946-4c69-b500-c39ec1b03a7d`}
</ExpectedOutput>
</Output>

`openshell --workspace dev sandbox get pi-agent` shows the same sandbox from the gateway's side: its id, phase and runtime.

</Step>

<Step n="3" title="Read the NetworkPolicy that pairs them">

The isolation between the two pods is ordinary Kubernetes **NetworkPolicy**: the gateway made three with the sandbox, next to the chart's SSH policy:

```bash
kubectl -n dev get networkpolicy
```
<Output>
<ExpectedOutput>
{`NAME                                              POD-SELECTOR
openshell-sandbox-supervisors                     openshell.ai/boundary-role=supervisor
openshell-sandbox-workloads                       openshell.ai/boundary-role=workload
openshell-workspace-sandbox-ssh                   openshell.ai/managed-by=openshell
os-control-64aee23c-9946-4c69-b500-c39ec1b03a7d   openshell.ai/boundary-pair=64aee23c-9946-4c69-b500-c39ec1b03a7d`}
</ExpectedOutput>
</Output>

Workload pods may talk only to their own supervisor (`os-control-<id>` matches the pair). The supervisor is the one with network access, and it applies the policy.

</Step>

<Section n="3" title="Test the seal from inside the sandbox">

The agent runs as the unprivileged user `sandbox`. Before it starts, the sandbox runtime applies the policy's static parts:

- **Landlock** (a Linux security module) limits the filesystem: `/usr`, `/lib`, `/etc` read-only, `/sandbox` and `/tmp` writable, everything else invisible. OpenShell 0.1 needs Landlock ABI v3, so the node needs Linux 6.2 or newer.
- **seccomp** filters dangerous system calls, and the process can't regain root.
- These are **static**: fixed when the sandbox is created.

<ReadScene scene="kernel" />

Kubernetes adds two guardrails of its own: a sandbox may use a cluster resource (a RuntimeClass, a PriorityClass, a volume) only if the operator labelled it `openshell.ai/sandbox-attachable=true`, and **Kyverno** rejects any sandbox pod that asks for the host's network, PID or IPC namespace.

Now check it. **`openshell --workspace dev sandbox exec -n pi-agent -- <command>`** runs one command inside the sandbox, through the gateway and the supervisor, and returns.

<Step n="1" title="Check which user the agent runs as">

Run `id` inside the sandbox to see which user the agent runs as:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- id
```
<Output summary="An unprivileged user, not root.">
<ExpectedOutput>
{`uid=10001 gid=10001 groups=10001`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Try to write outside /sandbox: Landlock refuses">

Landlock decides which paths the agent may read and write. Try to write in `/usr`, write in `/sandbox`, and list `/root`:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'touch /usr/x; touch /sandbox/x && echo "/sandbox is writable"; ls /root'
```
<Output>
<ExpectedOutput>
{`touch: cannot touch '/usr/x': Permission denied
/sandbox is writable
ls: cannot open directory '/root': Permission denied`}
</ExpectedOutput>
</Output>

Exactly the policy's `filesystem_policy`.

</Step>

<Step n="3" title="Try the Kubernetes API: no connection">

In 0.4 the agent's pod reached the API server with its ServiceAccount token. Here `curl` gets no connection at all (`-m 6` gives up after six seconds; exit 7 means it couldn't connect):

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'curl -sk -m 6 -o /dev/null https://kubernetes.default.svc.cluster.local/version || echo "blocked (curl exit $?)"'
```
<Output>
<ExpectedOutput>
{`blocked (curl exit 7)`}
</ExpectedOutput>
</Output>

</Step>

<Step n="4" title="Read the environment the supervisor prepared">

The supervisor prepares the agent's environment before it starts. Print the three variables that matter here:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'env | grep -E "^(HOME|LITELLM_API_KEY|SSL_CERT_FILE)" | cut -c1-80'
```
<Output>
<ExpectedOutput>
{`HOME=/sandbox
LITELLM_API_KEY=openshell:resolve:env:v6304638483022285593_LITELLM_API_KEY
SSL_CERT_FILE=/run/openshell-supervisor-ca/material/ca-bundle.crt`}
</ExpectedOutput>
</Output>

`LITELLM_API_KEY` is the placeholder from `dev`'s `litellm` provider. `SSL_CERT_FILE` points at a bundle that includes the supervisor's CA: that's how the supervisor can inspect HTTPS requests at L7 while the agent's TLS still validates.

</Step>

<Optional title="Explore with an interactive shell">

`openshell --workspace dev sandbox connect pi-agent` opens a shell **inside** the sandbox. Try `id`, `ls /`, `touch /usr/x`, `touch /sandbox/notes.txt`, then press **Ctrl-D** to come back (the sandbox keeps running):

```bash-interactive
openshell --workspace dev sandbox connect pi-agent
```

Type those commands at the sandbox prompt, not in the Cluster shell: there they'd show you the VM itself.

</Optional>

</Section>

<Section n="4" title="Run pi sealed: the model works, nothing else does">

In 0.4 the pod installed pi from npm at start. The sandbox image ships it already, and its network is closed, so there's nothing to install. Run it and repeat what it did in 0.4: the model call goes through, everything else stops at the boundary. (Installing from npm, and opening the door it needs, is the first thing you do in [1.5](/learn/policy).)

<Diagram id="pi-sealed" n="1.8" caption="What the next steps show: pi's model call matches the provider's rule and reaches LiteLLM with the real key; the curl its bash tool runs has no rule and gets no response; both decisions land in the audit log." />

<Step n="1" title="See how pi is pointed at LiteLLM, with the placeholder">

The image's `pi` command is a small launcher: on first use it copies `/etc/pi/models.json` and `settings.json` into `~/.pi/agent`. They're the same as the files in 0.4: LiteLLM's address, and `apiKey: "$LITELLM_API_KEY"`, a reference pi resolves from its environment. Here that variable holds the placeholder:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'pi --version; grep -E "baseUrl|apiKey|defaultModel" /etc/pi/models.json /etc/pi/settings.json'
```
<Output>
<ExpectedOutput>
{`1.5.2
/etc/pi/models.json:      "baseUrl": "http://litellm.litellm.svc.cluster.local:4000/v1",
/etc/pi/models.json:      "apiKey": "$LITELLM_API_KEY",
/etc/pi/settings.json:  "defaultModel": "default"`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Ask pi a question through LiteLLM">

The same question as in 0.4:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- pi --no-session -p "In one sentence: what is an AI agent harness?"
```
<Output summary="It answers: the model call went through the supervisor, which added the real key.">
<ExpectedOutput>
{`An AI agent harness is a framework that supplies the runtime infrastructure, tools, and interfaces needed to build, deploy, and manage autonomous AI agents that can perceive, reason, act, and interact with external systems.`}
</ExpectedOutput>
</Output>

</Step>

<Step n="3" title="Give it bash and the same curl task as in 0.4">

Give pi its `bash` tool and the same task as in 0.4: fetch example.com with curl and report the status code:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- pi --no-session --tools bash -p "Use bash to run curl -s -m 8 -o /dev/null -w %{http_code} https://example.com and reply with one line: the HTTP status it printed."
```
<Output summary="000: curl got no response. The agent still runs its tool; the network says no.">
<ExpectedOutput>
{`000`}
</ExpectedOutput>
</Output>

Unlike 0.4, this time there is a record. **`openshell --workspace dev logs pi-agent`** prints the sandbox's log; its `OCSF` lines are the audit events. They show both decisions: the model call allowed by the provider's L7 rule, and curl to example.com denied:

```bash
openshell --workspace dev logs pi-agent | grep OCSF | grep -E "example.com|litellm" | tail -3
```
<Output>
<ExpectedOutput>
{`[1794576987.271] [sandbox] [OCSF ] [ocsf] CONFIG:OBSERVATION [INFO] Policy DNS staged unapproved name example.com synthetic=198.18.0.3 for TCP policy review
[1794576987.274] [sandbox] [OCSF ] [ocsf] NET:OPEN [MED] DENIED /usr/bin/curl(0) -> example.com:443 [reason:transparent_tcp_policy_denied]
[1794576987.286] [sandbox] [OCSF ] [ocsf] HTTP:POST [INFO] ALLOWED POST http://litellm.litellm.svc.cluster.local:4000/v1/chat/completions [policy:_provider_litellm engine:l7]`}
</ExpectedOutput>
</Output>

</Step>

<Step n="4" title="Ask it to print its key: only a placeholder">

In 0.4 an agent with a shell could read the real key. Ask this one to print its key:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- pi --no-session --tools bash -p "Use bash to print the environment variable LITELLM_API_KEY and reply with only its value." | cut -c1-40
```
<Output summary="A placeholder. The real key only exists in the gateway and on the supervisor's outbound requests.">
<ExpectedOutput>
{`openshell:resolve:env:v16326338877800647`}
</ExpectedOutput>
</Output>

Keep `pi-agent` and the `dev` workspace: the next lab opens its network, rule by rule.

</Step>

<Optional title="The same agent, two places">

| | 0.4: an ordinary pod | 1.4: an OpenShell sandbox |
|---|---|---|
| Model key | the real key in its environment | a placeholder; the supervisor adds the key on allowed calls |
| Network | any host, and the Kubernetes API | only what the policy allows, per binary, method and path |
| Files | the whole container | `/sandbox` and `/tmp` writable, system paths read-only, the rest invisible |
| Audit | nothing in the pod's log | every allow and deny as an OCSF event |
| Changing it | edit the Deployment, restart | `openshell policy set` on the running sandbox |

</Optional>

<Callout type="lab" title="A sandbox is a pair of pods plus a policy">
No magic VM: a workload pod with a locked-down process, a supervisor pod that owns its network, and NetworkPolicy between them. Kubernetes gives you scheduling, lifecycle and RBAC; OpenShell adds the isolation, the policy and the audit trail on top.
</Callout>

## What you learned

<Learned next="/learn/policy" nextLabel="Open its network, rule by rule">

- **`openshell sandbox create` asks the gateway**, which writes a Sandbox resource and starts a supervisor pod; the controller makes the workload pod.
- **The seal holds from inside.** An unprivileged user, Landlock on the filesystem, no route to the Kubernetes API, and a placeholder instead of the key.
- **The network is deny by default.** curl was refused, the model call allowed, and both decisions are in the audit log.

</Learned>
