<Section n="2" title="LiteLLM: one gateway to your model">

An agent needs a model, and a cluster usually has more than one agent. Rather than hand each one the inference endpoint and its key, the cluster runs one **model gateway** in front of it. Agents call the gateway with a key of its own; the gateway knows the real endpoint and key, maps model names and aliases, and can add budgets, rate limits and logging in one place.

<Diagram id="gateway-place" n="0.2" caption="Where a model gateway sits: every agent in the cluster calls LiteLLM with LiteLLM's own key; only LiteLLM holds the real keys and talks to the model endpoints." />

This lab uses **[LiteLLM](https://www.litellm.ai/)**, an open-source gateway that offers one OpenAI-compatible API in front of more than a hundred model providers ([docs](https://docs.litellm.ai/)). Other gateways do the same job, and any of them would fit here:

| Gateway | What it is |
|---|---|
| [Envoy AI Gateway](https://aigateway.envoyproxy.io/) | Built on Envoy Gateway, which already fronts this lab's web traffic. Open source. |
| [Kong AI Gateway](https://konghq.com/products/kong-ai-gateway) | AI plugins for the Kong API gateway. Open source core. |
| [Portkey AI Gateway](https://portkey.ai/) | A lightweight open-source gateway, also offered as a hosted service. |


<Step n="1" title="The LiteLLM service">

LiteLLM runs like any other app on Kubernetes: a Deployment that keeps its pod running, and a Service in front of it, so other pods reach it by name on port 4000.

```bash
kubectl -n litellm get deploy,svc
```

<Step n="2" title="Its configuration">

LiteLLM reads its configuration from a ConfigMap. Its `model_list` is where your inference endpoint is set: it maps the model names agents ask for to the real model, its base URL and its key.

**Where its values come from.** When the Launchable was created, you (or whoever set it up) filled in three environment values. The VM's setup script wrote them to `.env`, and `scripts/setup.sh` handed them to the Ansible role `05-litellm`, which installed LiteLLM with its Helm chart. Each value ended up in one place:

| You gave the Launchable | Where it went | What you will see |
|---|---|---|
| `MODEL_BASE_URL` | ConfigMap `litellm-config` | `api_base`: the inference endpoint LiteLLM calls |
| `MODEL_NAME` | ConfigMap `litellm-config` | `model_name`, `model: openai/…` (the `openai/` prefix means "speak the OpenAI API to it"), and the target of the alias `default` |
| `MODEL_API_KEY` | Secret `litellm-secrets`, key `UPSTREAM_API_KEY` | only a reference: `api_key: os.environ/UPSTREAM_API_KEY`. The key itself is never in the config; the pod gets it as an environment variable |
| nothing: generated at setup | Secret `litellm-secrets`, key `LITELLM_MASTER_KEY` | not in the ConfigMap. It is LiteLLM's own key, which clients use instead of the upstream one; you'll use it in the next step |

Now read it:

```bash
kubectl -n litellm get configmap litellm-config -o jsonpath='{.data.config\.yaml}' | sed -n '/^model_list/,$p'
```
<Output summary="Your inference endpoint, behind one model name and the alias default.">
<ExpectedOutput>
{`model_list:
- litellm_params:
    api_base: <MODEL_BASE_URL>
    api_key: os.environ/UPSTREAM_API_KEY
    model: openai/<MODEL_NAME>
    stream_options:
      include_usage: true
  model_name: <MODEL_NAME>
router_settings:
  model_group_alias:
    default: <MODEL_NAME>`}
</ExpectedOutput>
</Output>

`default` is an alias: clients ask for `default`, and LiteLLM picks the real model. To point the lab at another model later, you change these values, not the agents.

</Step>

<Section n="3" title="Talk to the model through LiteLLM">

<Step n="1" title="Call LiteLLM from the VM">

The Service is only reachable inside the cluster, so open a short-lived port-forward, read the master key from its Secret (it's never printed), and call the OpenAI-compatible API:

```bash
KEY=$(kubectl -n litellm get secret litellm-secrets -o jsonpath='{.data.LITELLM_MASTER_KEY}' | base64 -d)
kubectl -n litellm port-forward svc/litellm 4000:4000 >/dev/null 2>&1 & PF=$!; sleep 3
curl -s localhost:4000/v1/models -H "Authorization: Bearer $KEY" | grep -o '"id":"[^"]*"'
curl -s localhost:4000/v1/chat/completions -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"default","messages":[{"role":"user","content":"Say hello in five words."}]}' | grep -o '"content":"[^"]*"'
kill $PF
```
<Output summary="The alias and your model, and an answer from it.">
<ExpectedOutput>
{`"id":"default"
"id":"<MODEL_NAME>"
"content":"\\n\\nHello, I hope you're well."`}
</ExpectedOutput>
</Output>

Any client with the master key can now call your model, from anywhere that can reach the Service. Keep that in mind for the next lab.

</Step>

## What you learned

<Learned next="/learn/agent-on-k8s" nextLabel="Deploy an agent on Kubernetes">

- **One VM, one Kubernetes node**, with each component in its own namespace.
- **LiteLLM is the model gateway.** The inference endpoint and its key live in its configuration and Secrets; clients use LiteLLM's own key and the alias `default`.
- **Whoever holds the LiteLLM key can call the model**, from anywhere that reaches the Service.

</Learned>
