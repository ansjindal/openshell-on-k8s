## The idea: a team of read-only specialists

When something breaks, you reach for four signals: **logs, metrics, traces, and what Kubernetes did**. So the fleet is four read-only specialists plus a lead analyst, each a pi agent in its own sandbox, using the **sre-tools** MCP server and the **platform skills** from Module 3:

- **logs** 🔎: may call `loki_query`, nothing else.
- **metrics** 📈: may call `prometheus_query`, nothing else.
- **traces** 🧵: may call `tempo_search`, nothing else.
- **events** 🛎️: may call `cluster_events` and `pod_status`: what the control plane changed, and which pods are missing.
- **analyst** 🧠: **no tools at all**; it concludes the others' findings into a root cause and a recommended fix.

Each agent's **policy names its tools**: the metrics agent can see that `loki_query` exists, but calling it is refused by its supervisor, and no agent can call `scale_deployment`. That's not a limitation to work around; it *is* the product: a fleet you can hand a production incident without widening anyone's blast radius, and prove it from the audit log.

<Callout type="note" title="Agents diagnose; humans fix">
The agents never hold Kubernetes credentials: the MCP server does, and the policy only lets them call read-only tools. So the loop is: the fleet finds the root cause, proposes a change, and a <strong>human approves</strong> before anything is applied. (In production that applied change is a git commit ArgoCD syncs: same shape, automated delivery.)
</Callout>

## The arc of this module

1. **Spin up the fleet**: one command brings five pi agents up, each with its role, the platform skills and a policy that allows only its tools.
2. **See it at a glance**: every agent's status, what it may reach and which tools it may call.
3. **Investigate an incident**: break the shop, and a conductor in this page asks each specialist for its evidence and the analyst for a verdict. You approve the fix.
4. **Under the hood** and **build your own**: the plan, the prompts, and how to add a specialist.
