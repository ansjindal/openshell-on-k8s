An **agent** is a model plus a **harness**: the program that sends your prompt to the model, runs the tools the model asks for, and feeds the results back until the model answers. Here you deploy one built with **pi**, a small open-source harness, the way agents usually reach production: a container, a Deployment, a Secret with an API key. Then you use it, and look at what it can reach from inside the cluster.

## What pi is

**pi** is a small, open-source **agent harness**: the program from [What is an agent?](/learn/what-is-an-agent) that runs the loop around a model. You give it a task; it sends the task to the model, the model answers with either text or a request to use a tool, pi runs that tool and sends the result back, and it goes round again until the model is done.

| Part of pi | What it is | In this lab |
|---|---|---|
| **The `pi` command** | Installed from npm as `@earendil-works/pi-coding-agent`. Run on its own it opens an interactive terminal chat; `pi -p "…"` runs one task and prints the answer. | The pod installs it at start; you run `pi -p` with `kubectl exec`. |
| **Models** | Any OpenAI-compatible (or Anthropic, Google) API, described in `~/.pi/agent/models.json`: a provider with a `baseUrl`, an API style, a key and the model ids. The key can be a reference such as `$LITELLM_API_KEY`, read from the environment when pi calls the model. | One provider, `lab`, pointing at LiteLLM, with the model `default`. |
| **Tools** | What the model may ask pi to do: `read`, `write`, `edit` and `bash` by default, plus `grep`, `find` and `ls`. `--tools bash` allows only the shell; `--no-tools` none. | First none, then `--tools bash`. |
| **Sessions** | pi keeps a history of each conversation under `~/.pi/agent/sessions/`. `--no-session` keeps nothing. | Every run is one-off. |
| **`PI_OFFLINE=1`** | Stops pi's own update check and install telemetry, so the only network calls are to the model. | Set in the Deployment. |

pi is only one harness among many (OpenClaw, Claude Code, Codex, OpenCode…); it's used here because it is small, scriptable and easy to point at any model. The point of this lab is not pi: it is what **any** harness can reach once it runs with real access.

<Section n="1" title="Deploy it" goal="Run pi as an ordinary Deployment in its own namespace.">

<Step n="1" title="A namespace and the key">

The agent needs a key for LiteLLM. Put LiteLLM's master key in a Secret in a new namespace, `agents` (it's never printed). `--dry-run … | kubectl apply` creates them, or updates them if they already exist, so you can run this again safely.

```bash
kubectl create namespace agents --dry-run=client -o yaml | kubectl apply -f -
kubectl -n agents create secret generic litellm-key \
  --from-literal=LITELLM_API_KEY="$(kubectl -n litellm get secret litellm-secrets -o jsonpath='{.data.LITELLM_MASTER_KEY}' | base64 -d)" \
  --dry-run=client -o yaml | kubectl apply -f -
```
<Output>
<ExpectedOutput>
{`namespace/agents created
secret/litellm-key created`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="The Deployment">

`manifests/agents/pi-agent.yaml` describes the agent. Part by part:

- **`kind: Deployment`, namespace `agents`, one replica.** An ordinary Kubernetes workload: Kubernetes keeps one pod of it running.
- **`image: node:22`.** A stock Node.js image, with a shell, `curl` and `npm`: everything a coding agent typically gets.
- **The startup script** (`command` and `args`) installs pi from npm (`@earendil-works/pi-coding-agent@1.5.2`), writes pi's model configuration, then sleeps, so you can `exec` in and use the agent.
- **pi's `models.json`** defines one provider, `lab`: `baseUrl` is LiteLLM's Service (`http://litellm.litellm.svc.cluster.local:4000/v1`), `api: openai-completions` because LiteLLM speaks the OpenAI API, `apiKey: "$LITELLM_API_KEY"` tells pi to read the key from that environment variable, and the one model is `default`, LiteLLM's alias for your model.
- **`env`.** `LITELLM_API_KEY` comes from the Secret you just made (`secretKeyRef`), so the **real key** sits in the agent's environment. `PI_OFFLINE=1` stops pi's own update check.
- **`readinessProbe`** waits for `/tmp/ready`, written once pi is installed, so the rollout below finishes only when the agent can be used.
- **`resources`.** Half a gigabyte requested, at most two.

<Optional title="Show the whole manifest">

```yaml
# Module 0 lab: the pi agent as an ordinary Kubernetes workload. It gets the
# LiteLLM key as an environment variable, installs pi from npm at start, and
# points it at LiteLLM in the cluster.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pi-agent
  namespace: agents
spec:
  replicas: 1
  selector:
    matchLabels: { app: pi-agent }
  template:
    metadata:
      labels: { app: pi-agent }
    spec:
      containers:
        - name: agent
          image: node:22
          env:
            - name: PI_OFFLINE
              value: "1"
            - name: LITELLM_API_KEY
              valueFrom:
                secretKeyRef: { name: litellm-key, key: LITELLM_API_KEY }
          command: ["bash", "-c"]
          args:
            - |
              npm install -g --no-audit --no-fund @earendil-works/pi-coding-agent@1.5.2
              mkdir -p ~/.pi/agent
              cat > ~/.pi/agent/models.json <<'JSON'
              {
                "providers": {
                  "lab": {
                    "baseUrl": "http://litellm.litellm.svc.cluster.local:4000/v1",
                    "api": "openai-completions",
                    "apiKey": "$LITELLM_API_KEY",
                    "compat": { "supportsDeveloperRole": false, "supportsReasoningEffort": false },
                    "models": [{ "id": "default" }]
                  }
                }
              }
              JSON
              touch /tmp/ready
              sleep infinity
          readinessProbe:
            exec: { command: ["test", "-f", "/tmp/ready"] }
            periodSeconds: 3
          resources:
            requests: { memory: 512Mi }
            limits: { memory: 2Gi }
```

<Section n="2" title="Use it" goal="Ask it something, then give it a shell.">

<Step n="1" title="Ask it something">

```bash

```

<Section n="3" title="What it holds, and what it can reach" goal="Look at the agent's pod the way an attacker would.">

<Step n="1" title="Its key and the cluster">

```bash
kubectl -n agents exec deploy/pi-agent -- bash -c 'echo "LITELLM_API_KEY: ${LITELLM_API_KEY:0:3}… (${#LITELLM_API_KEY} characters)"; curl -sk -m 5 -o /dev/null -w "Kubernetes API with its token: HTTP %{http_code}\n" -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" https://kubernetes.default.svc/api'
```
<Output summary="The real LiteLLM key is in its environment, and its pod can talk to the Kubernetes API.">
<ExpectedOutput>
{`LITELLM_API_KEY: sk-… (51 characters)
Kubernetes API with its token: HTTP 200`}
</ExpectedOutput>
</Output>

Anything the agent runs (a tool, a script, an installed package, a command a prompt talked it into) can read that key, send it anywhere on the internet, and probe the cluster from the inside. That is the default for an agent deployed as an ordinary workload.

</Step>

## What you learned

<Learned next="/learn/agent-misled" nextLabel="When an agent is misled">

- **Deploying an agent is ordinary Kubernetes**: an image, a Deployment, a Secret with a key.
- **Ordinary means unbounded.** From its pod the agent reached the internet, held the real LiteLLM key and talked to the Kubernetes API.
- **Nothing records what it does.** No log tells you which hosts it called, or why.

</Learned>
