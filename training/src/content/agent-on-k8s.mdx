An **agent** is a model plus a **harness**: the program that sends your prompt to the model, runs the tools the model asks for, and feeds the results back until the model answers. Here you deploy one built with **pi**, a small open-source harness, the way agents usually reach production: a container, a Deployment, a Secret with an API key. Then you use it, and look at what it can reach from inside the cluster.

## What a harness is

A model on its own only turns text into text: it can't run a command, open a file or remember yesterday. The **harness** is the program around it that makes it an agent. Whatever the harness, it does the same few jobs:

- **The loop.** Send the task to the model; if the answer asks for a tool, run it, send the result back, and repeat until the model gives a final answer.
- **Tools.** Decide what the model may ask for: a shell, reading and editing files, a web browser, search, or any service exposed through [MCP](https://modelcontextprotocol.io/).
- **Context.** Build what the model sees each turn: a system prompt, the conversation so far, project files, skills, memory.
- **The model connection.** Which API to call, with which key and model name.
- **Permissions.** Whether to ask a person before running a tool, and which commands or paths to allow. These checks live inside the harness, in the same process as the agent.

Many harnesses exist, and new ones appear every month. A few you may meet:

| Harness | What it is |
|---|---|
| [pi](https://github.com/earendil-works/pi) | A minimal open-source coding agent for the terminal, with any model. The one you use throughout this course. |
| [OpenClaw](https://openclaw.ai/) | An open-source personal assistant agent that runs on your own machine and talks to you through chat apps. |
| [Claude Code](https://github.com/anthropics/claude-code) | Anthropic's coding agent for the terminal and IDEs. |
| [Codex CLI](https://github.com/openai/codex) | OpenAI's open-source coding agent for the terminal. |
| [Gemini CLI](https://github.com/google-gemini/gemini-cli) | Google's open-source agent for the terminal. |
| [OpenCode](https://opencode.ai/) | An open-source terminal coding agent that works with many model providers. |
| [Goose](https://github.com/aaif-goose/goose) | An open-source, extensible agent built around MCP extensions, with a desktop app and a CLI. |
| [OpenHands](https://github.com/OpenHands/OpenHands) | An open-source platform for software agents that write code, run commands and browse. |
| [Aider](https://aider.chat/) | AI pair programming in your terminal, working in your git repository. |

They differ in their tools, their prompts and how they ask permission. They share one thing: each runs its tools with the rights of wherever it runs. In a container on Kubernetes, that is the pod.

## What pi is

**pi** is a small, open-source **agent harness** ([github.com/earendil-works/pi](https://github.com/earendil-works/pi)). You give it a task; it sends the task to the model, the model answers with either text or a request to use a tool, pi runs that tool and sends the result back, and it goes round again until the model is done.

| Part of pi | What it is | In this lab |
|---|---|---|
| **The `pi` command** | Installed from npm as `@earendil-works/pi-coding-agent`. Run on its own it opens an interactive terminal chat; `pi -p "…"` runs one task and prints the answer. | The pod installs it at start; you run `pi -p` with `kubectl exec`. |
| **Models** | Any OpenAI-compatible (or Anthropic, Google) API, described in `~/.pi/agent/models.json`: a provider with a `baseUrl`, an API style, a key and the model ids. The key can be a reference such as `$LITELLM_API_KEY`, read from the environment when pi calls the model. | One provider, `lab`, pointing at LiteLLM, with the model `default`. |
| **Tools** | What the model may ask pi to do: `read`, `write`, `edit` and `bash` by default, plus `grep`, `find` and `ls`. `--tools bash` allows only the shell; `--no-tools` none. | First none, then `--tools bash`. |
| **Sessions** | pi keeps a history of each conversation under `~/.pi/agent/sessions/`. `--no-session` keeps nothing. | Every run is one-off. |
| **`PI_OFFLINE=1`** | Stops pi's own update check and install telemetry, so the only network calls are to the model. | Set in the Deployment. |

This lab uses pi because it is small, scriptable and easy to point at any model. The point is not pi: it is what **any** harness can reach once it runs with real access, as you'll see below.

<Section n="1" title="Deploy pi as an ordinary Kubernetes Deployment">

<Step n="1" title="Create the agents namespace and a Secret with the LiteLLM key">

The agent gets its own namespace, `agents`, and a key for LiteLLM in a Secret there, the usual way to hand a workload an API key. Line by line:

- **`kubectl create namespace agents`** makes the namespace.
- **`kubectl -n agents create secret generic litellm-key`** makes a Secret named `litellm-key` with one entry, `LITELLM_API_KEY`.
- **`--from-literal=LITELLM_API_KEY="$(…)"`** fills that entry with LiteLLM's master key, read from the Secret `litellm-secrets` you met in 0.3 (`-o jsonpath` picks the field, `base64 -d` decodes it). It goes straight from one Secret to the other and is never printed.
- **`--dry-run=client -o yaml | kubectl apply -f -`** on both lines: instead of creating the object directly, `kubectl` only writes it out as YAML, and `kubectl apply` creates it, or updates it if it already exists. A plain `create` would fail the second time; this way you can run the step again safely.

```bash
kubectl create namespace agents --dry-run=client -o yaml | kubectl apply -f -
kubectl -n agents create secret generic litellm-key \
  --from-literal=LITELLM_API_KEY="$(kubectl -n litellm get secret litellm-secrets -o jsonpath='{.data.LITELLM_MASTER_KEY}' | base64 -d)" \
  --dry-run=client -o yaml | kubectl apply -f -
```

{`namespace/agents created
secret/litellm-key created`}
</ExpectedOutput>
</Output>

</Step>

<YamlRead id="pi-agent-deployment" />

Apply it and wait for it. **`kubectl apply -f`** sends the manifest to the API server, which creates the Deployment; the scheduler places its pod on the node, and the kubelet starts it. **`kubectl rollout status`** waits until the pod is Ready, which here means pi is installed (about half a minute), or gives up after four minutes:

```bash
cd ~/openshell-on-k8s && kubectl apply -f manifests/agents/pi-agent.yaml && kubectl -n agents rollout status deploy/pi-agent --timeout=240s
```

<Section n="2" title="Use the agent: a question, a shell command, and what its logs show">

<Step n="1" title="Ask a question: text only, no tools">

**`kubectl -n agents exec deploy/pi-agent --`** runs a command inside the agent's pod, as if you had a shell there. The command is `pi`:

- **`--provider lab --model default`** picks the provider from its `models.json` (LiteLLM) and the model `default`.
- **`--no-session`** keeps no conversation history.
- **`-p "…"`** runs one task and prints the answer, instead of opening the interactive chat.

No `--tools` flag here, so the model can only answer in text.

```bash
kubectl -n agents exec deploy/pi-agent -- pi --provider lab --model default --no-session -p "In one sentence: what is an AI agent harness?"
```
<Output summary="The answer came from your model, through LiteLLM.">
<ExpectedOutput>
{`An AI agent harness is a framework that provides the infrastructure, tools, and orchestration capabilities to build, deploy, and manage autonomous AI agents that can perceive, reason, and act in environments.`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Let it use bash: fetch a web page from inside the pod">

The same call with **`--tools bash`**: now the model may ask pi to run shell commands in the pod. The task asks it to fetch `https://example.com` with `curl` and report the HTTP status. The model doesn't run anything itself: it asks for a `bash` tool call, pi runs it in the pod, and sends the result back.

```bash
kubectl -n agents exec deploy/pi-agent -- pi --provider lab --model default --no-session --tools bash -p "Use bash to run curl -s -m 8 -o /dev/null -w %{http_code} https://example.com and reply with one line: the HTTP status it printed."
```
<Output summary="200: from inside the cluster, the agent reaches the internet.">
<ExpectedOutput>
{`200`}
</ExpectedOutput>
</Output>

</Step>

<Step n="3" title="Read the pod's logs: what did they record?">

The agent just ran a shell command and reached the internet. Ask Kubernetes what the pod logged. **`kubectl logs`** prints what the pod's container wrote to its standard output and error, the usual first place to look when something happens in a pod:

```bash
kubectl -n agents logs deploy/pi-agent
```
<Output summary="Only the install: nothing about the task, the tool call or the request to example.com.">
<ExpectedOutput>
{`npm warn deprecated node-domexception@1.0.0: Use your platform's native DOMException instead

added 123 packages in 12s
npm notice
npm notice New major version of npm available! 10.9.9 -> 12.2.2
npm notice Changelog: https://github.com/npm/cli/releases/tag/v12.2.2
npm notice To update run: npm install -g npm@12.2.2
npm notice`}
</ExpectedOutput>
</Output>

That is the startup script's `npm install`, and nothing else. Your `pi` runs came in through `kubectl exec`, which doesn't write to the pod's log, and pi itself logs nothing. LiteLLM's own log shows the model calls (`POST /v1/chat/completions` from the pod's IP), but the `curl` to `example.com` went straight from the pod to the internet: **no component saw it**, and nothing says what the agent ran or why.

</Step>

</Section>

<Section n="3" title="Check what the agent holds and what it can reach">

Look at the agent's pod the way an attacker would: what could anything running in it use?

<Step n="1" title="Check the key in its environment and its access to the Kubernetes API">

One shell command run inside the agent's pod (`bash -c '…'`) checks the two things anything running there can use:

- **`${LITELLM_API_KEY:0:3}` and `${#LITELLM_API_KEY}`** print only the first three characters of the key and its length: enough to show the real key is in the environment, without printing it.
- **`curl … https://kubernetes.default.svc/api`** calls the Kubernetes API server from inside the pod, with the **ServiceAccount token** Kubernetes mounts into every pod by default (`/var/run/secrets/kubernetes.io/serviceaccount/token`). `-k` skips certificate checks, `-m 5` gives up after five seconds, and `-w` prints only the HTTP status.

```bash
kubectl -n agents exec deploy/pi-agent -- bash -c 'echo "LITELLM_API_KEY: ${LITELLM_API_KEY:0:3}… (${#LITELLM_API_KEY} characters)"; curl -sk -m 5 -o /dev/null -w "Kubernetes API with its token: HTTP %{http_code}\n" -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" https://kubernetes.default.svc/api'
```
<Output summary="The real LiteLLM key is in its environment, and its pod can talk to the Kubernetes API.">
<ExpectedOutput>
{`LITELLM_API_KEY: sk-… (51 characters)
Kubernetes API with its token: HTTP 200`}
</ExpectedOutput>
</Output>

Anything the agent runs (a tool, a script, an installed package, a command a prompt talked it into) can read that key, send it anywhere on the internet, and probe the cluster from the inside. That is the default for an agent deployed as an ordinary workload.

</Step>

</Section>

## What you learned

<Diagram id="agent-unbounded" n="0.3" caption="What you saw in this lab: the agent's pod holds the real key and its ServiceAccount token, and reaches the model, any host on the internet and the Kubernetes API. Only the model calls pass anything that records them." />

<Learned next="/learn/agent-misled" nextLabel="When an agent is misled">

- **Deploying an agent is ordinary Kubernetes**: an image, a Deployment, a Secret with a key.
- **Ordinary means unbounded.** From its pod the agent reached the internet, held the real LiteLLM key and talked to the Kubernetes API.
- **Nothing records what it does.** No log tells you which hosts it called, or why.

</Learned>
