The kernel holds the agent's process in; the **supervisor** decides where it may go. Both are configured by one short YAML file per sandbox. Here is that file, then you open the network on a running sandbox one rule at a time.

## The supervisor pod: what the agent can reach

The workload pod has no network of its own. A Kubernetes **NetworkPolicy** lets it talk only to its supervisor, and the supervisor decides everything else:

- **Deny by default.** Nothing leaves unless a `network_policies` entry allows it.
- **L4**: which host and port, from which binary (`curl` may reach GitHub, `python3` may not).
- **L7**: for `protocol: rest`, which HTTP method and path, even inside TLS. `GET /repos/**` allowed, `DELETE` refused with `403 policy_denied`.
- **Live**: network rules are **dynamic**; a new revision loads into a running sandbox without a restart.

## The policy file, line by line

Every layer of a sandbox is configured by one short YAML file: its **policy**. You'll edit policies in almost every lab, so here it is line by line. Press **Next** to step through it: the lines that matter light up on the left, and on the right you see what they let through and what they stop.

<DeckScene src="openshell" only="policy" title="One YAML file, two lifetimes" />

| Part | Controls | Enforced by | Changes on a running sandbox? |
|---|---|---|---|
| `filesystem_policy` | paths readable / writable | Landlock, in the kernel | no, fixed at creation |
| `landlock` | how strict if the kernel lacks a Landlock feature | the sandbox runtime | no |
| `process` | the user and group the agent runs as | the sandbox runtime | no |
| `network_policies` | hosts, ports, methods, paths, programs | the supervisor | **yes**: `openshell policy update` / `policy set` |

A few details the labs rely on:

- **Deny by default.** An empty `network_policies` means no network at all. Each entry opens one door.
- **`enforcement`** defaults to `audit` (log, but allow). Write `enforce` to block.
- **`access`** presets: `read-only` (GET, HEAD, OPTIONS), `read-write`, `full`. For finer control, L7 rules name methods and paths.
- **Providers** add their own entry, such as `_provider_litellm`, when you attach them; you don't write it.
- **Hosts are full names** (`litellm.litellm.svc.cluster.local`), because the sandbox resolves names without search domains.

<Callout type="warn" title="Defense in depth, not a silver bullet">
No single layer is the answer. Landlock and seccomp bound the process, the supervisor bounds the network, providers bound the secrets, identities bound the control plane, and the audit trail tells you what happened. Together they make a compromised agent a contained problem instead of a cluster-wide one.
</Callout>

## Exercise: the seal, rule by rule

A sandbox's network is governed by its **policy**. Every connection the agent opens goes to its **supervisor**, which allows it only if a `network_policies` entry says so: deny by default, with a short allow-list you control.

<Section n="1" title="What the sandbox may reach today" goal="Read the effective policy, including what providers added.">

<Step n="1" title="The policy and its version">

Ask the gateway for `agent-0`'s policy: its version, hash and status.

```bash
openshell policy get agent-0
```


</Step>

<Step n="2" title="The full effective policy">

The **effective** policy includes what attached providers added. Under `network_policies` you'll find `_provider_litellm`, merged in from the `litellm` provider's profile: its endpoint, its L7 rules and the binaries allowed to use them. Anything not listed is denied, and every decision is audited.

```bash
openshell policy get agent-0 --full
```
<Output>
<ExpectedOutput>
{`network_policies:
  _provider_litellm:
    endpoints:
      - host: litellm.litellm.svc.cluster.local
        port: 4000
        protocol: rest
        enforcement: enforce
        rules:
          - allow: {method: GET, path: /v1/models}
          - allow: {method: POST, path: /v1/chat/completions}
          ...
    binaries:
      - path: /**`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="2" title="Deny by default, in practice" goal="Prove the internet is closed to the agent.">

<Step n="1" title="Try GitHub from inside the sandbox">

```bash
openshell sandbox exec -n agent-0 -- curl -s -m 8 -o /dev/null -w 'HTTP %{http_code}\n' https://api.github.com/zen
```

<Output>
<ExpectedOutput>
{`HTTP 000`}
</ExpectedOutput>
</Output>

`000` means no HTTP response at all: the supervisor refused the connection. No cluster API, no internet, nothing you didn't grant.

</Step>

</Section>

<Section n="3" title="Grant one endpoint, live" goal="Open GitHub's API for GET only, while the sandbox runs.">

<Step n="1" title="Add a read-only endpoint">

The endpoint format is `host:port[:access[:protocol[:enforcement]]]`, and the rule applies only to the binaries you name with `--binary`:

```bash
openshell policy update agent-0 --add-endpoint 'api.github.com:443:read-only:rest:enforce' --binary /usr/bin/curl --wait
```
<Output>
<ExpectedOutput>
{`✓ Policy version 2 submitted (hash: ae09c7816c51)
✓ Policy version 2 loaded (active version: 2)`}
</ExpectedOutput>
</Output>

The new revision loaded into the **running** sandbox, with no restart. The parts of the rule:

- `read-only`: an access preset: `GET`, `HEAD` and `OPTIONS` only.
- `rest`: inspect requests at **L7** (method and path), even inside TLS.
- `enforce`: block what breaks the rule. The default is `audit`, which only logs.

</Step>

<Step n="2" title="GET now works">

```bash
openshell sandbox exec -n agent-0 -- curl -s -m 10 -w ' HTTP %{http_code}\n' https://api.github.com/zen
```
<Output>
<ExpectedOutput>
{`Responsive is better than fast. HTTP 200`}
</ExpectedOutput>
</Output>

</Step>

<Step n="3" title="POST is refused at L7">

A `POST` to the same host is refused by the supervisor, with the reason:

```bash
openshell sandbox exec -n agent-0 -- curl -s -m 10 -X POST -d '{}' -w '\nHTTP %{http_code}\n' https://api.github.com/markdown
```
<Output>
<ExpectedOutput>
{`{"error":"policy_denied","policy":"allow_api_github_com_443","rule":"POST /markdown","detail":"POST /markdown not permitted by policy","layer":"l7",...}
HTTP 403`}
</ExpectedOutput>
</Output>

</Step>

</Section>

## Exercise: beyond REST, TCP egress

[The Seal](/learn/security) covered REST endpoints, where the supervisor inspects every request and filters by method and path. Not everything is HTTP: a database connection, an MQTT broker, any raw TCP service. For those the policy has a plainer endpoint: **host and port, no request inspection**, an L4 allow.

<Section n="5" title="The two endpoint shapes" goal="Preview a REST rule and a bare L4 rule side by side.">

<Step n="1" title="Preview a REST rule">

Preview a REST rule with `--dry-run` (it prints the merged policy and sends nothing):

```bash
openshell policy update agent-0 --add-endpoint 'api.github.com:443:read-only:rest:enforce' --binary /usr/bin/curl --dry-run | grep -A12 'allow_api_github_com_443:'
```
<Output>
<ExpectedOutput>
{`allow_api_github_com_443:
  name: allow_api_github_com_443
  endpoints:
    - host: api.github.com
      port: 443
      protocol: rest
      enforcement: enforce
      access: read-only
  binaries:
    - path: /usr/bin/curl`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Preview the bare form">

…and compare the bare form, just `host:port`:

```bash
openshell policy update agent-0 --add-endpoint 'example.com:443' --binary /usr/bin/curl --dry-run | grep -A7 'allow_example_com_443:'
```
<Output>
<ExpectedOutput>
{`allow_example_com_443:
  name: allow_example_com_443
  endpoints:
    - host: example.com
      port: 443
  binaries:
    - path: /usr/bin/curl`}
</ExpectedOutput>
</Output>

That's the whole difference. The REST rule carries `protocol`, `enforcement` and `access`: the supervisor inspects every request. The bare entry has none: no protocol parsing, no method or path filtering. It's a firewall-style allow for one host, one port and the named binaries.

<Callout type="nv" title="Why this exists">
A sandbox that needs Postgres, an MQTT broker or any raw TCP service has no verbs or paths to filter on. The L4 form gives it a real allow rule without pretending to inspect a protocol the supervisor can't parse. Deny by default still holds for every other host and port, and for every binary you didn't name.
</Callout>

</Step>

</Section>

<Section n="6" title="Try it" goal="Apply the L4 rule and test its host and binary limits.">

<Step n="1" title="Apply the bare rule">

```bash
openshell policy update agent-0 --add-endpoint 'example.com:443' --binary /usr/bin/curl --wait
```

</Step>

<Step n="2" title="curl reaches the host">

```bash
openshell sandbox exec -n agent-0 -- curl -s -o /dev/null -w 'HTTP %{http_code}\n' https://example.com/
```
<Output>
<ExpectedOutput>
{`HTTP 200`}
</ExpectedOutput>
</Output>

</Step>

<Step n="3" title="Every other host is still closed">

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -m 8 -o /dev/null https://example.org/ || echo "blocked (curl exit $?)"'
```
<Output>
<ExpectedOutput>
{`blocked (curl exit 7)`}
</ExpectedOutput>
</Output>

</Step>

<Step n="4" title="Another binary is refused">

The rule is **per binary**: Python, going to the very same host, is refused:

```bash
openshell sandbox exec -n agent-0 -- python3 -c 'import urllib.request; print(urllib.request.urlopen("https://example.com").status)'
```
<Output>
<ExpectedOutput>
{`urllib.error.URLError: <urlopen error [Errno 13] Permission denied>`}
</ExpectedOutput>
</Output>

That binary check is what stops an agent from exfiltrating data through an unexpected tool, even to a host it's allowed to reach. Every one of these decisions is in the audit trail; you'll read it in [The Audit Trail](/learn/audit).

</Step>

</Section>
