In [1.4](/learn/build-an-agent) `pi-agent` ran sealed: the model worked, curl got nowhere. Real agents need more: a package registry, an API to read, a database to query. Here you open the network rule by rule, **while the sandbox runs**: first with a policy file, then one rule at a time, and see how narrow each rule can be: one host, one HTTP method, one program.

## How network rules work

The workload pod has no network of its own (the NetworkPolicy from 1.4 lets it reach only its supervisor), and the supervisor decides everything else:

- **Deny by default.** Nothing leaves unless a `network_policies` entry allows it. Each entry opens one door.
- **L4**: which host and port, from which program (`curl` may reach a host, `python3` may not).
- **L7**: for `protocol: rest`, which HTTP method and path, even inside TLS.
- **Live**: network rules are **dynamic**; a new revision loads into a running sandbox without a restart. Files and process stay as they were at creation.

A few details the steps below rely on:

- **`enforcement`** defaults to `audit` (log, but allow). Write `enforce` to block.
- **`access`** presets: `read-only` (GET, HEAD, OPTIONS), `read-write`, `full`. For finer control, rules name methods and paths.
- **Providers** add their own entry, such as `_provider_litellm`, when you attach them; you don't write it.
- **Hosts are full names** (`litellm.litellm.svc.cluster.local`), because the sandbox resolves names without search domains.

<Section n="1" title="Install a package from npm: refused, then one door opened with a policy file">

Agents often install tools while they run, as the Module 0 pod installed pi at start. Try that in `pi-agent`: with the baseline policy the network is closed, so you'll open exactly one door, with a policy file.

<Step n="1" title="Ask npm for pi: the connection is refused">

The sandbox image has Node and npm. Ask the npm registry for pi's latest version (`--fetch-retries=0 --fetch-timeout=5000` makes it fail fast instead of retrying):

openshell --workspace dev sandbox exec -n pi-agent -- npm view @earendil-works/pi-coding-agent version --fetch-retries=0 --fetch-timeout=5000

The supervisor wrote down why, in the sandbox's audit log:

<Step n="2" title="Read the policy file, then open one door for npm">

Every layer of a sandbox is set by one short YAML file: its **policy**. The baseline you created `pi-agent` with is one; here it is line by line, with what each part lets through and what it stops:

<ReadScene scene="policy" />

| Part | Controls | Enforced by | Changes on a running sandbox? |
|---|---|---|---|
| `filesystem_policy` | paths readable / writable | Landlock, in the kernel | no, fixed at creation |
| `landlock` | how strict if the kernel lacks a Landlock feature | the sandbox runtime | no |
| `process` | the user and group the agent runs as | the sandbox runtime | no |
| `network_policies` | hosts, ports, methods, paths, programs | the supervisor | **yes**: `openshell policy set` / `policy update` |

`manifests/policies/pi-agent.yaml` is the baseline plus one grant: the npm registry, **read-only**, for **`/usr/bin/node` only**.

<YamlRead id="pi-agent-policy" />

**`openshell --workspace dev policy set`** replaces the sandbox's policy with a file; `--wait` returns once the supervisor has loaded it:

```bash
cd ~/openshell-on-k8s && openshell --workspace dev policy set pi-agent --policy manifests/policies/pi-agent.yaml --wait
```
<Output summary="Revision 2 is loaded into the running sandbox: no restart.">
<ExpectedOutput>
{`✓ Policy version 2 submitted (hash: 6750e23ab498)
✓ Policy version 2 loaded (active version: 2)`}
</ExpectedOutput>
</Output>

</Step>

<Section n="3" title="Open GitHub's API for GET only, while it runs">

Open one HTTP API for one method only, while the sandbox keeps running, and see both sides of the rule.

<Step n="1" title="Try GitHub first: no response">

`-w 'HTTP %{http_code}'` makes curl print the status code; `000` means there was no HTTP response at all:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- curl -s -m 8 -o /dev/null -w 'HTTP %{http_code}\n' https://api.github.com/zen
```
<Output summary="No response: no rule allows api.github.com.">
<ExpectedOutput>
{`HTTP 000`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Add a read-only rule for curl">

**`openshell policy update`** changes one part of the policy instead of replacing the file. `--add-endpoint` takes `host:port[:access[:protocol[:enforcement]]]`, and the rule applies only to the programs you name with `--binary`:

```bash
openshell --workspace dev policy update pi-agent --add-endpoint 'api.github.com:443:read-only:rest:enforce' --binary /usr/bin/curl --wait
```
<Output summary="Revision 3, loaded into the running sandbox.">
<ExpectedOutput>
{`✓ Policy version 3 submitted (hash: 80d45453fd59)
✓ Policy version 3 loaded (active version: 3)`}
</ExpectedOutput>
</Output>

The parts of the rule:

- `read-only`: the access preset, `GET`, `HEAD` and `OPTIONS` only.
- `rest`: inspect each request at **L7** (method and path), even inside TLS.
- `enforce`: block what breaks the rule, instead of only logging it.

</Step>

<Step n="3" title="Call GitHub with GET: it works">

Repeat the GET that got no response a minute ago:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- curl -s -m 10 -w ' HTTP %{http_code}\n' https://api.github.com/zen
```
<Output>
<ExpectedOutput>
{`Encourage flow. HTTP 200`}
</ExpectedOutput>
</Output>

</Step>

<Step n="4" title="POST is refused at L7">

A `POST` to the same host, from the same program, is refused by the supervisor, which says exactly why:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- curl -s -m 10 -X POST -d '{}' -w '\nHTTP %{http_code}\n' https://api.github.com/markdown
```
<Output summary="403 from the supervisor: POST /markdown matches no rule.">
<ExpectedOutput>
{`{"error":"policy_denied","policy":"allow_api_github_com_443","rule":"POST /markdown","detail":"POST /markdown not permitted by policy","layer":"l7",...}
HTTP 403`}
</ExpectedOutput>
</Output>

<Section n="4" title="Open a non-HTTP door with a plain TCP rule">

Not everything is HTTP: a database, an MQTT broker, any raw TCP service has no methods or paths to inspect. For those the policy has a plainer endpoint: **host and port only**, an L4 allow.

<Step n="1" title="Preview the rule before applying it">

The bare form of `--add-endpoint` is just `host:port`. `--dry-run` prints the merged policy and sends nothing:

```bash
openshell --workspace dev policy update pi-agent --add-endpoint 'example.com:443' --binary /usr/bin/curl --dry-run | grep -A7 'allow_example_com_443:'
```
<Output>
<ExpectedOutput>
{`allow_example_com_443:
  name: allow_example_com_443
  endpoints:
    - host: example.com
      port: 443
  binaries:
    - path: /usr/bin/curl`}
</ExpectedOutput>
</Output>

Compare it with the GitHub rule: no `protocol`, `enforcement` or `access`. No request parsing, no method or path filtering: one host, one port, the named programs.

</Step>

<Step n="2" title="Apply the TCP rule">

Apply the same rule for real; `--wait` returns once the supervisor has loaded it:

```bash
openshell --workspace dev policy update pi-agent --add-endpoint 'example.com:443' --binary /usr/bin/curl --wait
```
<Output>
<ExpectedOutput>
{`✓ Policy version 4 submitted (hash: 57ae5fc61fa7)
✓ Policy version 4 loaded (active version: 4)`}
</ExpectedOutput>
</Output>

</Step>

<Step n="3" title="Check that curl reaches example.com">

Repeat the request pi's tool made in 1.4, which got `000` then:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- curl -s -o /dev/null -w 'HTTP %{http_code}\n' https://example.com/
```
<Output>
<ExpectedOutput>
{`HTTP 200`}
</ExpectedOutput>
</Output>

</Step>

<Step n="4" title="Check that every other host is still closed">

The rule opened one host. Try a different one, `example.org`:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- sh -c 'curl -s -m 8 -o /dev/null https://example.org/ || echo "blocked (curl exit $?)"'
```
<Output>
<ExpectedOutput>
{`blocked (curl exit 7)`}
</ExpectedOutput>
</Output>

</Step>

<Step n="5" title="Try the same host from Python: refused">

The rule is **per program**: Python, going to the very same host, is refused:

```bash
openshell --workspace dev sandbox exec -n pi-agent -- python3 -c 'import urllib.request; print(urllib.request.urlopen("https://example.com").status)'
```
<Output>
<ExpectedOutput>
{`urllib.error.URLError: <urlopen error [Errno 13] Permission denied>`}
</ExpectedOutput>
</Output>

That program check is what stops an agent from sending data out through an unexpected tool, even to a host it's allowed to reach.

</Step>

</Section>

<Callout type="warn" title="Defense in depth, not a silver bullet">
No single layer is the answer. Landlock and seccomp bound the process, the supervisor bounds the network, providers bound the secrets, identities bound the control plane, and the audit trail tells you what happened. Together they make a compromised agent a contained problem instead of a cluster-wide one.
</Callout>

## What you learned

<Learned next="/learn/os-check" nextLabel="Summary & knowledge check">

- **The effective policy** is your file plus what providers add; anything not listed is denied.
- **A policy file sets the starting rules.** `policy set` replaced the baseline with one read-only door for npm, for `node` only.
- **Rules change live.** `policy update --add-endpoint` loads a new revision into the running sandbox.
- **L7 rules filter by method and path**: GET allowed, POST refused with the reason.
- **L4 rules** allow one host and port for the named programs only, for traffic that isn't HTTP.
- **Every change is a revision** you can list and read back.

</Learned>
