Five specialists, each with its own policy, tools, skills and role, is a lot to repeat by hand. So the fleet is written down in **one file**, `fleet.txt`, and brought up by **one script**, `scripts/fleet.sh`, which runs the same steps you ran by hand in Modules 1 and 3, once per agent.

<Section n="1" title="Read the fleet's spec, fleet.txt">

`fleet.txt`, at the top of the repository, is the whole fleet: **one agent per line**, its name and the sre-tools MCP tools it may call.

<Step n="1" title="Print fleet.txt">

```bash
cat ~/openshell-on-k8s/fleet.txt
```
<Output>
<ExpectedOutput>
{`# The SRE copilot fleet: one pi agent per line, whitespace-separated columns:
#   name      sre-tools MCP tools this agent may call (comma-separated, or "-" for none)
# Each agent gets its role from manifests/fleet/roles/<name>.md, the platform
# skills from the skill repository, and a policy that allows ONLY its tools.
logs      loki_query
metrics   prometheus_query
traces    tempo_search
events    cluster_events,pod_status
analyst   -`}
</ExpectedOutput>
</Output>

- **The name** is the sandbox's name, and picks its role file, `manifests/fleet/roles/<name>.md`.
- **The tools** are what its policy will allow, comma-separated; `-` means none. The analyst has none: it only reasons over the others' findings.

<Section n="4" title="See every agent's reach on one page">

The panel below reads the fleet live from the cluster. Each card is one agent:

- **Status**: `Ready` means the gateway has the sandbox up and its policy loaded.
- **May reach**: the hosts in its *effective* policy. Every agent reaches LiteLLM (through the provider) and the skill repository; the specialists also reach the **sre-tools** MCP server.
- **May call**: the tools its MCP rule allows, exactly the ones on its line of `fleet.txt`.
- **ROLE.md**: the role the agent was given.

<FleetView />

There's no honor system here. If the `metrics` agent tried `loki_query`, its supervisor would refuse the call, and the denial would be in its audit log, with the tool's name and the rule. No agent may call `scale_deployment`.

</Section>

<Step n="2" title="Read one agent's MCP rule">

The policy is where each agent becomes a specialist. Read the `metrics` agent's MCP rule from its effective policy:

```bash
openshell policy get metrics --full | sed -n '/^  sre_tools:/,$p'
```
<Output summary="Only prometheus_query may be called; scale_deployment is denied.">
<ExpectedOutput>
{`  sre_tools:
    name: sre_tools
    endpoints:
      - host: sre-tools.tools.svc.cluster.local
        path: /mcp
        port: 8080
        protocol: mcp
        enforcement: enforce
        rules:
          - allow:
              method: initialize
          - allow:
              method: notifications/initialized
          - allow:
              method: tools/list
          - allow:
              method: tools/call

                  - prometheus_query

          - method: tools/call

The other entries are `_provider_litellm` (the model) and `skill_repo` (the skills). `logs`, `traces` and `events` get the same rule with their own tools; `analyst` gets no `sre_tools` rule at all.

</Step>

<Step n="3" title="Read one agent's role">

The role is plain Markdown, handed to pi with `--append-system-prompt /sandbox/ROLE.md`:

```bash
openshell sandbox exec -n metrics -- cat /sandbox/ROLE.md
```
<Output>
<ExpectedOutput>
{`# Role: Gauge, the metrics specialist

You investigate **metrics only**, with the sre-tools \`prometheus_query\` tool. It
is the only tool your policy lets you call.

Quantify the incident: the shop's request rate by HTTP code
(\`sum by (code) (rate(shop_requests_total{namespace="demo"}[2m]))\`, where 5xx is

</ExpectedOutput>

**Role + tools + skills + a policy that names the tools = a specialist**, and every line of it is readable. The skills are the same for every agent (`k8s-triage`, `incident-report`, `demo-app-map` from Module 3): change one in the skill repository, re-run `fleet.sh up`, and the whole fleet has it.

</Step>

<Step n="4" title="Tear the fleet down (later, not now)">

When you're **done with the course**, this removes the fleet. Don't run it now:

```bash-ref
./scripts/fleet.sh down fleet.txt
```

</Step>

<Callout type="note" title="Why this stays safe to scale">
Adding an agent is one line in <code>fleet.txt</code> and one role file. It never widens the trust boundary: the new agent may call exactly the tools on its line, that grant is in its policy, and every call it makes is in the audit log.
</Callout>

## What you learned

<Learned next="/learn/incident-lab" nextLabel="Investigate an incident">

- **One spec, one script.** `fleet.txt` names each agent and its tools; `fleet.sh` writes the policy, creates the sandbox and configures pi, the same steps you did by hand.
- **The policy makes the specialist**: an MCP rule that names its tools, plus a read-only clone of the skills.
- **Every agent's reach is readable**, on its card and in its policy; roles and skills are files in git.

</Learned>
