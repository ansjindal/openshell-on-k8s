You don't want to repeat 1.4 and Module 3 by hand for every specialist: workspace, sandbox, policy, pi, its model, its MCP server, its skills. So the fleet is described in **one spec** and brought up by **one helper** that does all of it, in a loop.

<BeforeYouStart
  will="read the one-file fleet spec, bring five pi agents up with one helper, see them on the cluster, read one agent's MCP rule and its role."
  time="about ten minutes, most of it waiting for the sandboxes to be Ready."
/>

<Section n="1" title="The spec: one agent per line">

`fleet.txt` is the whole fleet: **one agent per line, two whitespace-separated columns**, the agent's name and the sre-tools MCP tools it may call:

```text
logs      loki_query
metrics   prometheus_query
traces    tempo_search
events    cluster_events,pod_status
analyst   -
```

- **`name`**: the sandbox's name, and its role file, `manifests/fleet/roles/<name>.md`.
- **`tools`**: the sre-tools tools its policy allows, comma-separated; `-` means none. The analyst has none: it only reasons over the others' findings.

</Section>

<Section n="2" title="Bring the fleet up">

For each line, `scripts/fleet.sh`:

1. writes a **policy** that allows only a read-only clone of the skill repository and, if the agent has tools, the sre-tools MCP server for **those tools only** (the same `protocol: mcp` rule as 3.3, with `scale_deployment` always denied);
2. creates the sandbox in the platform workspace, `lab`, with the `litellm` provider;
3. adds the sre-tools server to pi's `mcp.json` (pi ships in the sandbox image, already pointed at LiteLLM), clones the **platform skills** into `~/.agents/skills`, and writes the agent's **role** to `/sandbox/ROLE.md`.

The agents need no package egress at all: everything they run comes with the image.

<Step n="1" title="Run the helper">

```bash
./scripts/fleet.sh up fleet.txt
```

<Step n="2" title="One agent's MCP rule">

The policy is where each agent becomes a specialist. Read the `metrics` agent's MCP rule from its effective policy:

```bash
openshell policy get metrics --full | sed -n '/^  sre_tools:/,$p'
```
<Output summary="Only prometheus_query may be called; scale_deployment is denied.">
<ExpectedOutput>
{`  sre_tools:
    name: sre_tools
    endpoints:
      - host: sre-tools.tools.svc.cluster.local
        path: /mcp
        port: 8080
        protocol: mcp
        enforcement: enforce
        rules:
          - allow:
              method: initialize
          - allow:
              method: notifications/initialized
          - allow:
              method: tools/list
          - allow:
              method: tools/call
              tool:
                any:
                  - prometheus_query
        deny_rules:
          - method: tools/call
            tool: scale_deployment
        mcp:
          versions:
            - '2025-03-26'

</ExpectedOutput>
</Output>

The other entries are `_provider_litellm` (the model) and `skill_repo` (the skills). `logs`, `traces` and `events` get the same rule with their own tools; `analyst` gets no `sre_tools` rule at all.

</Step>

<Step n="3" title="One agent's role">

The role is plain Markdown, handed to pi with `--append-system-prompt /sandbox/ROLE.md`:

```bash
openshell sandbox exec -n metrics -- cat /sandbox/ROLE.md
```
<Output>
<ExpectedOutput>
{`# Role: Gauge, the metrics specialist

You investigate **metrics only**, with the sre-tools \`prometheus_query\` tool. It
is the only tool your policy lets you call.

Quantify the incident: the shop's request rate by HTTP code
(\`sum by (code) (rate(shop_requests_total{namespace="demo"}[2m]))\`, where 5xx is
the error rate) and each Deployment's available replicas
(\`kube_deployment_status_replicas_available{namespace="demo"}\`). Report the
numbers that matter. Never invent numbers. The analyst concludes.`}
</ExpectedOutput>
</Output>

**Role + tools + skills + a policy that names the tools = a specialist**, and every line of it is readable. The skills are the same for every agent (`k8s-triage`, `incident-report`, `demo-app-map` from Module 3): change one in the skill repository, re-run `fleet.sh up`, and the whole fleet has it.

</Step>

<Step n="4" title="Tearing down (later)">

When you're **done with the course**, this removes the fleet. Don't run it now:

```bash-ref
./scripts/fleet.sh down fleet.txt
```

</Step>

</Section>

<Callout type="note" title="Why this stays safe to scale">
Adding an agent is one line in <code>fleet.txt</code> and one role file. It never widens the trust boundary: the new agent may call exactly the tools on its line, that grant is in its policy, and every call it makes is in the audit log.
</Callout>

## What you learned

<Learned next="/learn/fleet-status" nextLabel="The fleet at a glance">

- **One spec, one helper.** `fleet.txt` names each agent and its tools; `fleet.sh` does the rest.
- **pi comes with the image**: the agents need no package egress.
- **The policy makes the specialist**: an MCP rule that names its tools, plus the skill repository.
- **Roles and skills are files** you can read, review and change in git.

</Learned>
