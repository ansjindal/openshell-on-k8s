The fleet you built is a **pattern**, not a fixed thing: *a sealed agent = a role + the tools its policy names + the platform skills*, and a no-tools analyst that concludes. Adding to it never widens the trust boundary: each new agent may call exactly the tools on its line, in its own policy, and every call is in the audit log. Here are concrete directions to take it on your own.

## A new specialist: the alerts agent 🚨

You already have logs, metrics, traces and events. Add a fifth that reads **Alertmanager**, what's *already firing*, so the fleet starts from the alerts.

1. **A tool**: add `alerts_firing()` to the sre-tools MCP server (`manifests/tools/sre-tools/server.mjs`): one `registerTool` that calls `http://kps-kube-prometheus-stack-alertmanager.monitoring.svc.cluster.local:9093/api/v2/alerts` and returns alertname, severity and the object. Apply with `kubectl apply -k manifests/tools` and restart the Deployment.
2. **A line**: in `fleet.txt`:

   ```text
   alerts    alerts_firing
   ```
3. **A role**: `manifests/fleet/roles/alerts.md`: "you read firing alerts only; surface alertname, severity and the object."
4. **A call**: add `alerts` to `PROBES` in the orchestrator, then `./scripts/fleet.sh up fleet.txt`.

## A new skill for every agent

Skills are the cheapest way to make the whole fleet better. Add one to the skill repository ([3.4](/learn/skill-repo)): for example `slo-math`, which explains how to turn request rates into an error budget burn rate. Lint it, push it, and re-run `fleet.sh up`: every agent clones it. No policy changes, no new access.

## A new fault: make the signals combine

Scaling a dependency to zero is clean: events alone crack it. Inject something that needs the fleet to **reconcile several signals**:

- **CrashLoopBackOff**: ship a bad command. `events` shows BackOff, `logs` shows the crash output, `metrics` shows restarts climbing. The analyst has to weave all three.
- **Bad config**: mount a ConfigMap with a wrong value. The app starts (no image or scaling event), logs errors, traces get slow. Several angles, one cause.

Wire it as another action in `training/src/app/api/incident/route.ts`, next to `break`.

## Let the fleet propose the fix as a change

Today the approved fix is a `kubectl` command behind your confirm, and no agent may call `scale_deployment`. In production, make "Apply fix" open a **pull request** instead: the analyst's recommended action becomes a one-line commit a reviewer approves and **ArgoCD** syncs. The human gate doesn't move; only the delivery does.

## Point it at your workload

The tools take a namespace, and the orchestrator's `INCIDENT_NS` sets which one the plan uses. Deploy your own app, set `INCIDENT_NS`, and the same fleet investigates *your* namespace. Nothing about the pattern is specific to `demo`.

<Callout type="rh" title="The test of a good pattern">
Every idea above is the <em>same few moves</em>: a tool in the MCP server, a line naming who may call it, a role, a skill. If extending a multi-agent system is a handful of small, reviewable changes, and never a new way to widen who can reach what, you've built something you can actually operate. That's the point of the whole course.
</Callout>
