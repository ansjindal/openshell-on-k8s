## 1 · Enter OpenShell

The last module ended with a requirement: a boundary outside the agent's process, which it can't see into, argue with or switch off. **NVIDIA OpenShell** is an open-source runtime that builds exactly that. It puts the whole agent process in a sandbox governed by a YAML policy: you declare what the agent may touch, and OpenShell enforces it from outside.

## 3 · How OpenShell is built

**OpenShell** is what makes "run an autonomous agent *safely*" practical. In one line: **to be useful, agents need access; to be safe, they need zero trust**, and OpenShell is the runtime that gives you both. It is a gateway plus guardrails, built on the open-source `agent-sandbox` Kubernetes primitive.

<Fig id="sandbox-anatomy" n="1.1" caption="A sandbox is a workload pod and a supervisor pod, inside its workspace's namespace." />

### The pieces

- **Gateway**: the control plane, a gRPC API (`openshell` CLI, the console, the SDKs). It stores sandboxes, policies with their revision history, provider profiles and provider credentials, and checks every call against the caller's identity and role.
- **Compute driver**: the part of the gateway that speaks Kubernetes. It writes `agents.x-k8s.io` `Sandbox` resources and creates the supervisor pods, so OpenShell doesn't reinvent scheduling.
- **Supervisor**: one per sandbox, in its own pod. It is the sandbox's only way out: it resolves DNS, evaluates every connection and request against the policy, injects provider credentials, relays `exec` and SSH, and writes an **OCSF** audit event for each decision.
- **Sandbox runtime**: inside the workload pod. It starts the agent as an unprivileged `sandbox` user under **Landlock** (filesystem) and **seccomp**, and hands all network traffic to the supervisor.

### The objects you work with

| Object | What it is | CLI |
|---|---|---|
| Sandbox | One isolated agent environment (two pods) | `openshell sandbox create / list / exec / delete` |
| Policy | Filesystem, process and network rules; versioned, network rules live-updatable | `openshell policy get / update / set / list` |
| Provider profile | A *kind* of credential: which env vars, which endpoints, which L7 rules | `openshell profile import / describe / export` |
| Provider | A credential instance of a profile, stored by the gateway | `openshell provider create / update / list` |
| Workspace | A tenant: its own sandboxes, providers and members | `openshell workspace create / member add`, `--workspace` on any command, the console |

### Who may call the gateway

Every call carries an identity:

- **People** sign in with **Keycloak** (OIDC). Their token's realm roles decide what they can do: `openshell-admin` is a platform admin, `openshell-user` works inside the workspaces they belong to.
- **The lab operator** (this VM's CLI and scripts) presents a client certificate with `OU=operator`, issued by cert-manager. It is a platform admin across all workspaces.
- **Supervisors** authenticate with tokens the gateway mints for their sandbox only.

### Why a control plane at all?

You *could* hand-write `Sandbox` resources with `kubectl`. The gateway exists so every sandbox gets a policy, a supervisor, credentials as placeholders, an identity and an audit trail, without you wiring those up each time:

```bash-ref
openshell sandbox list
```

<Callout type="tip" title="Two front doors, one cluster">
Everything you do through <code>openshell</code> shows up as ordinary Kubernetes objects. The control plane lives in <code>openshell</code>; each workspace's sandboxes live in a namespace the gateway creates for it, such as <code>openshell-lab-default</code>. You can always drop to <code>kubectl -n openshell-lab-default get sandboxes,pods</code> to see what the gateway did.
</Callout>

## 6 · Inside the sandbox: the kernel

### The workload pod: what the agent process can touch

The agent runs as the unprivileged user `sandbox`. The sandbox runtime applies the policy's static parts before the agent starts:

- **Landlock** (a Linux security module) limits the filesystem: here `/usr`, `/lib`, `/etc` are read-only, `/sandbox` and `/tmp` are writable, everything else is invisible. OpenShell 0.1 requires Landlock ABI v3, so the node needs Linux 6.2 or newer.
- **seccomp** filters dangerous system calls, and the process cannot regain root.
- These are **static**: fixed when the sandbox is created.

<ReadScene scene="kernel" />

### Kubernetes guardrails

- **Resource admission**: a sandbox may use a cluster resource (a RuntimeClass, a PriorityClass, a volume) only if the operator labelled it `openshell.ai/sandbox-attachable=true`.
- **Kyverno** rejects any sandbox pod that asks for the host's network, PID or IPC namespace.

## 7 · The policy file

### The supervisor pod: what the agent can reach

The workload pod has no network of its own. A Kubernetes **NetworkPolicy** lets it talk only to its supervisor, and the supervisor decides everything else:

- **Deny by default.** Nothing leaves unless a `network_policies` entry allows it.
- **L4**: which host and port, from which binary (`curl` may reach GitHub, `python3` may not).
- **L7**: for `protocol: rest`, which HTTP method and path, even inside TLS. `GET /repos/**` allowed, `DELETE` refused with `403 policy_denied`.
- **Live**: network rules are **dynamic**; a new revision loads into a running sandbox without a restart.

### The policy file, line by line

Every layer of a sandbox is configured by one short YAML file: its **policy**. You'll edit policies in almost every lab, so here it is line by line. Press **Next** to step through it: the lines that matter light up on the left, and on the right you see what they let through and what they stop.

<ReadScene scene="policy" />

| Part | Controls | Enforced by | Changes on a running sandbox? |
|---|---|---|---|
| `filesystem_policy` | paths readable / writable | Landlock, in the kernel | no, fixed at creation |
| `landlock` | how strict if the kernel lacks a Landlock feature | the sandbox runtime | no |
| `process` | the user and group the agent runs as | the sandbox runtime | no |
| `network_policies` | hosts, ports, methods, paths, programs | the supervisor | **yes**: `openshell policy update` / `policy set` |

A few details the labs rely on:

- **Deny by default.** An empty `network_policies` means no network at all. Each entry opens one door.
- **`enforcement`** defaults to `audit` (log, but allow). Write `enforce` to block.
- **`access`** presets: `read-only` (GET, HEAD, OPTIONS), `read-write`, `full`. For finer control, L7 rules name methods and paths.
- **Providers** add their own entry, such as `_provider_litellm`, when you attach them; you don't write it.
- **Hosts are full names** (`litellm.litellm.svc.cluster.local`), because the sandbox resolves names without search domains.

<Callout type="warn" title="Defense in depth, not a silver bullet">
No single layer is the answer. Landlock and seccomp bound the process, the supervisor bounds the network, providers bound the secrets, identities bound the control plane, and the audit trail tells you what happened. Together they make a compromised agent a contained problem instead of a cluster-wide one.
</Callout>

You ask the gateway for a sandbox. It writes a `Sandbox` resource and starts a supervisor pod; the controller turns the resource into the workload pod running OpenClaw. When the agent calls LiteLLM, the supervisor checks the request against the sandbox's policy, swaps the placeholder in `Authorization` for the real key, and forwards it.

<Callout type="note" title="The mental model">
A sandbox is a pair of pods plus a policy. Creating an agent means creating a sandbox; deleting it tears both pods down. Everything else, isolation, policy, credentials and audit, hangs off that.

<FigTour id="architecture" n="1.3" caption="The whole lab on one VM. Two workspaces, each its own namespace, with their sandboxes running inside." />

### Each component in a sentence

- **k3s**: single-node upstream Kubernetes. Lightweight, but a real cluster: the same CRDs, RBAC, NetworkPolicy and scheduler you'd use anywhere. The kubeconfig is `/etc/rancher/k3s/k3s.yaml`.
- **agent-sandbox controller**: [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox). It reconciles each `Sandbox` custom resource (`agents.x-k8s.io`) into a pod, the way a Deployment controller reconciles ReplicaSets.
- **OpenShell gateway** (namespace `openshell`): the control plane. It creates sandboxes, stores their policies and provider credentials, and decides who may do what. The CLI reaches it on NodePort **30808**.
- **Sandboxes** (one namespace per workspace, e.g. `openshell-lab-default`, created by the gateway): each one is **two pods**, the agent's workload pod and its supervisor pod. The supervisor owns the agent's network.
- **LiteLLM** (namespace `litellm`): one OpenAI-compatible endpoint in front of the model. Agents reach it through the `litellm` **provider**, with a key they never see.
- **Keycloak**, **Envoy Gateway** and the **OpenShell Console**: people sign in with Keycloak; Envoy publishes the training site, Keycloak and Grafana on one host and the console on its own.
- **Monitoring**: Prometheus and Grafana for metrics, Loki for logs and OpenShell's audit events, Tempo for traces.
- **OpenClaw 🦞**: the default agent, baked into the default sandbox image `ghcr.io/ansjindal/openshell-on-k8s/openclaw-sandbox`.

### Two layers, one policy

**NVIDIA OpenShell** is open-source software: the secure runtime boundary around every agent. It sits outside the model and the harness, so it works with open and closed models, and it runs on any Linux host (x86 or Arm), on bare metal, Docker or Kubernetes. This course is all OpenShell.

**NVIDIA Sentry** is a reference system design on **NVIDIA BlueField-4**. It moves the network decision off the host, onto a processor with its own CPU and operating system:

- **DOCA Tower** enforces the same OpenShell policy file.
- **DOCA Argus** tells it which program on the host sent each request.
- Root on the host can't rewrite either, and can't wipe what they record.

Together the two are the **NVIDIA Open Agent Safety Platform**. You deploy the layers your risk calls for:

| Outcome | No boundary | OpenShell | OpenShell + Sentry |
|---|---|---|---|
| Agent stays on approved sites and APIs | ✕ | ✓ | ✓ |
| Every request checked against your policy | ✕ | ✓ | ✓ |
| Survives a compromised host | ✕ | ✕ | ✓ |
| Enforced in hardware, outside the host | ✕ | ✕ | ✓ |

<Learned next="/learn/deploy" nextLabel="Lab 1.2: Verify OpenShell">

- **The boundary sits outside the agent.** OpenShell sandboxes the whole agent process; the agent can only ask.
- **Gateway and supervisor.** The gateway governs sandboxes, policies and keys; a supervisor per sandbox decides every connection, and fails closed.
- **Kernel and policy.** seccomp and Landlock hold the process in; one YAML policy sets files and process at startup and the network live.
- **Keys and evidence.** The agent holds placeholders, the supervisor adds the real key only for allowed endpoints, and every decision is an OCSF event.
