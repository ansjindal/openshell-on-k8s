<Section n="2" title="A team of read-only specialists">

When something breaks, you reach for four signals: **logs, metrics, traces, and what Kubernetes did**. So the fleet is four read-only specialists plus a lead analyst, each a pi agent in its own sandbox, using the **sre-tools** MCP server and the **platform skills** from Module 3:

- **logs** may call `loki_query`, nothing else.
- **metrics** may call `prometheus_query`, nothing else.
- **traces** may call `tempo_search`, nothing else.
- **events** may call `cluster_events` and `pod_status`: what the control plane changed, and which pods are missing.
- **analyst** has **no tools at all**; it combines the others' findings into a root cause and a recommended fix.

Each agent's **policy names its tools**: the metrics agent can see that `loki_query` exists, but its supervisor refuses the call, and no agent can call `scale_deployment`. That isn't a limitation to work around; it *is* the product: a fleet you can hand a production incident without widening anyone's blast radius, and prove it from the audit log.

<Callout type="note" title="Agents diagnose; people fix">
The agents never hold Kubernetes credentials: the MCP server does, and the policy only lets them call read-only tools. So the loop is: the fleet finds the root cause and proposes a change, and a <strong>person approves</strong> it before anything is applied. In production that change would be a git commit that Argo CD syncs: the same shape, with automated delivery.
</Callout>
