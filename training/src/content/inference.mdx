In [0.3](/learn/cluster-and-model) you met LiteLLM, the model gateway, and called it with its master key. An agent in an OpenShell sandbox needs the model too, but it must **never hold that key**: anything the agent runs could read it and send it anywhere, as you saw in [0.4](/learn/agent-on-k8s). OpenShell's answer is an **inference provider**: the key stays in the gateway, and the sandbox gets a placeholder.

## What a provider is

A **provider** is a credential the OpenShell gateway stores and hands to sandboxes **by reference**. It has three parts:

| Part | What it is | For `litellm` |
|---|---|---|
| **Profile** (the provider's *type*) | The access contract, written once in YAML: which credentials the provider has, which environment variable each becomes in a sandbox, how it is sent (here a bearer token in `Authorization`), and which endpoints and requests it may be sent to. | `ansible/roles/10-cli_providers/files/litellm-profile.yaml`: one credential, `LITELLM_API_KEY`, for `litellm.litellm.svc.cluster.local:4000`, model calls only. |
| **Provider** | An instance of a profile, with the real credential values, stored by the gateway. | `litellm`, holding LiteLLM's master key. |
| **Attachment** | A sandbox gets a provider with `--provider <name>` when it's created, or `openshell sandbox provider attach` later. | Every sandbox in this course. |

Once attached:

1. the sandbox's environment gets each credential as a **placeholder**, such as `LITELLM_API_KEY=openshell:resolve:env:…`;
2. the provider's endpoints and rules are merged into the sandbox's policy as `_provider_litellm`;
3. when the agent sends a request with the placeholder, the **supervisor** checks it against those rules and, only if it matches, swaps in the real key on the way out. Anything else is refused before a key is ever attached.

The provider was created when the machine was set up, by Ansible (`ansible/roles/10-cli_providers`), with LiteLLM's master key in the environment:

```bash-ref
openshell profile import -f litellm-profile.yaml --global
openshell provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY
```

`--credential LITELLM_API_KEY` reads the value from that environment variable, so the key never appears on a command line. `--global-profile` uses the profile imported for every workspace.

<Section n="1" title="Look at the litellm provider and the profile behind it">

What the gateway hands a sandbox for model access.

<Step n="1" title="List the providers the gateway stores">

Model access is an OpenShell **provider** named `litellm`, created at provisioning:

```bash
openshell provider list
```
<Output>
<ExpectedOutput>
{`NAME     TYPE     CREDENTIAL_KEYS   CONFIG_KEYS
litellm  litellm  1                 0`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Read its profile: the access contract">

Its type is a **provider profile**, the access contract: which variable the sandbox gets, where the credential may go, and which requests are allowed there:

```bash
openshell profile describe litellm
```
<Output>
<ExpectedOutput>
{`Credentials:
  api_key (required)
    Environment variables: LITELLM_API_KEY
    Authentication: bearer
    Header: authorization

Endpoints (declared policy):
  litellm.litellm.svc.cluster.local
    Ports: 4000
    Protocol: rest
    Access: custom rules
    Rules: 6 allow, 0 deny
    Enforcement: enforce`}
</ExpectedOutput>
</Output>

The six rules are model calls only: `GET /v1/models`, `POST /v1/chat/completions`, `/v1/completions`, `/v1/responses`, `/v1/embeddings`, `/v1/messages`. The file is `ansible/roles/10-cli_providers/files/litellm-profile.yaml`.

</Step>

</Section>

<Section n="2" title="What a sandbox sees: a placeholder that still works">

<Step n="1" title="Read the key in agent-0's environment">

`agent-0` is the sandbox the platform created at setup (you listed it in [1.2](/learn/deploy)), with `--provider litellm`. `openshell sandbox exec -n agent-0 -- …` runs one command inside it. Print the variable the provider gave it:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'echo $LITELLM_API_KEY'
```
<Output>
<ExpectedOutput>
{`openshell:resolve:env:v1535812..._LITELLM_API_KEY`}
</ExpectedOutput>
</Output>

A placeholder. There is no key anywhere in the sandbox to steal.

</Step>

<Step n="2" title="Use the placeholder to list the models">

Now call LiteLLM with it, exactly as you did with the master key in 0.3:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -H "Authorization: Bearer $LITELLM_API_KEY" http://litellm.litellm.svc.cluster.local:4000/v1/models | head -c 300; echo'
```

LiteLLM answers with its model list, so it received the **real** key: the supervisor swapped it in on the way.

</Step>

<Step n="3" title="Ask the model one question">

And a one-line chat completion with the same placeholder:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s http://litellm.litellm.svc.cluster.local:4000/v1/chat/completions -H "Authorization: Bearer $LITELLM_API_KEY" -H "Content-Type: application/json" -d "{\"model\":\"default\",\"messages\":[{\"role\":\"user\",\"content\":\"Say hello in five words.\"}]}" | grep -o "\"content\":\"[^\"]*\""'
```

</Step>

</Section>

<Section n="3" title="See what the placeholder can't be used for">

<Step n="1" title="Try LiteLLM's admin API: refused at L7">

The same key would open LiteLLM's **admin API** (create keys, read spend). The profile doesn't allow it, so the supervisor refuses before anything leaves the sandbox:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -X POST -H "Authorization: Bearer $LITELLM_API_KEY" http://litellm.litellm.svc.cluster.local:4000/key/generate; echo'
```
<Output>
<ExpectedOutput>
{`{"error":"policy_denied","policy":"_provider_litellm","rule":"POST /key/generate","detail":"POST /key/generate not permitted by policy","layer":"l7",...}`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="4" title="Change the model later, in one place">

Every sandbox reaches the model through LiteLLM, so the model is one setting, not something each agent knows. The values you gave the Launchable ([0.3.2](/learn/cluster-and-model)) live in `~/openshell-on-k8s/.env`. Edit `MODEL_NAME` (or `MODEL_BASE_URL` and `MODEL_API_KEY`) there, then apply it with the LiteLLM tag only, from the Cluster shell:

```bash-interactive
ANSIBLE_TAGS=litellm ./scripts/setup.sh
```

The `default` alias follows the new model; sandboxes, providers and policies don't change.

</Section>

<Callout type="note" title="What changed from older OpenShell">
Earlier releases routed every sandbox through a managed endpoint, <code>inference.local</code>. OpenShell 0.1 removed it: a sandbox reaches a model only through a provider you attach to <em>that</em> sandbox, and the agent calls the model's own API. Access is per sandbox and explicit, and the provider's L7 rules define exactly which calls are allowed.
</Callout>

## What you learned

<Learned next="/learn/build-an-agent" nextLabel="Bring up a sandboxed agent">

- **A provider is a credential the gateway keeps**, an instance of a profile. `litellm` holds LiteLLM's key; its profile says which variable a sandbox gets and which requests may carry the key.
- **The sandbox holds a placeholder.** It still works: the supervisor puts the real key on allowed calls on the way out.
- **Everything else is refused at L7**, before any key is attached: the admin API never sees a request.
- **The model is one setting**, in LiteLLM, not in any agent.
