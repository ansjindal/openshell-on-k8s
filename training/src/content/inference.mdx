In [0.3](/learn/cluster-and-model) you met LiteLLM, the model gateway, and called it with its master key. An agent in an OpenShell sandbox needs the model too, but it must **never hold that key**: anything the agent runs could read it and send it anywhere, as you saw in [0.4](/learn/agent-on-k8s). OpenShell's answer is an **inference provider**: the key stays in the gateway, and the sandbox gets a placeholder.

## What a provider is

A **provider** is a credential the OpenShell gateway stores and hands to sandboxes **by reference**. It has three parts:

| Part | What it is | For `litellm` |
|---|---|---|
| **Profile** (the provider's *type*) | The access contract, written once in YAML: which credentials the provider has, which environment variable each becomes in a sandbox, how it is sent (here a bearer token in `Authorization`), and which endpoints and requests it may be sent to. | `ansible/roles/10-cli_providers/files/litellm-profile.yaml`: one credential, `LITELLM_API_KEY`, for `litellm.litellm.svc.cluster.local:4000`, model calls only. |
| **Provider** | An instance of a profile, with the real credential values, stored by the gateway. | `litellm`, holding LiteLLM's master key. |
| **Attachment** | A sandbox gets a provider with `--provider <name>` when it's created, or `openshell sandbox provider attach` later. | Every sandbox in this course. |

Once attached:

1. the sandbox's environment gets each credential as a **placeholder**, such as `LITELLM_API_KEY=openshell:resolve:env:…`;
2. the provider's endpoints and rules are merged into the sandbox's policy as `_provider_litellm`;
3. when the agent sends a request with the placeholder, the **supervisor** checks it against those rules and, only if it matches, swaps in the real key on the way out. Anything else is refused before a key is ever attached.

For the platform's workspace `lab`, these two commands ran at setup (`ansible/roles/10-cli_providers`), with LiteLLM's master key in the environment. You run the second one yourself in Section 2, for your own workspace:

```bash-ref
openshell profile import -f litellm-profile.yaml --global
openshell provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY
```

`--credential LITELLM_API_KEY` reads the value from that environment variable, so the key never appears on a command line. `--global-profile` uses the profile imported for every workspace.

<Section n="2" title="Create your own workspace and add the litellm provider to it">

Providers belong to a **workspace**, OpenShell's tenant: its own sandboxes, providers and members. So to add a provider of your own, first make a workspace of your own. On this cluster each workspace is a Kubernetes **namespace of the same name**: the gateway runs in *operator mode*, so it doesn't create namespaces; you prepare one with a Helm chart, mark it as a workspace, and the gateway uses it. The platform's own workspace, `lab` (where `agent-0` runs), was made this way at setup. Now make yours, `dev`: your agent will run there in [1.4](/learn/build-an-agent).

<Step n="1" title="Install the openshell-workspace chart, which creates the namespace">

NVIDIA's **`openshell-workspace`** Helm chart, the same version as the gateway, puts what sandboxes need into a namespace. The chart itself doesn't make a namespace, so `--create-namespace` asks Helm to create `dev` first:

```bash
helm upgrade --install openshell-workspace oci://ghcr.io/nvidia/openshell/openshell-workspace --version 0.1.7 --namespace dev --create-namespace --wait
```
<Output summary="One Helm release in dev.">
<ExpectedOutput>
{`Release "openshell-workspace" does not exist. Installing it now.
NAME: openshell-workspace
NAMESPACE: dev
STATUS: deployed
REVISION: 1`}
</ExpectedOutput>
</Output>

List what it made:

```bash
kubectl -n dev get serviceaccount,role,rolebinding,networkpolicy
```
<Output>
<ExpectedOutput>
{`NAME                               AGE
serviceaccount/default             2s
serviceaccount/openshell-sandbox   0s

NAME                                                         CREATED AT
role.rbac.authorization.k8s.io/openshell-workspace-sandbox   2026-11-13T10:33:06Z

</ExpectedOutput>

- **`openshell-sandbox`**: the ServiceAccount sandbox pods run as. It has no Kubernetes permissions of its own.
- **Role and RoleBinding `openshell-workspace-sandbox`**: let the **gateway's** ServiceAccount (in `openshell`) create and manage `Sandbox` resources, pods and Secrets in **this** namespace only.
- **NetworkPolicy `openshell-workspace-sandbox-ssh`**: only the gateway's pods may reach sandboxes for `exec` and `connect`.

</Step>

<Step n="2" title="Label the namespace so the gateway may run sandboxes there">

The chart prepares the namespace, but it doesn't make it a workspace: Helm can create a namespace, not label it. The gateway places sandboxes only in namespaces labelled `openshell.ai/workspace=true` (its `operatorNamespaceLabel` setting). That's the platform admin's allowlist, kept apart from the chart on purpose: installing a chart into a namespace is not enough to let agents run there.

```bash
kubectl label namespace dev openshell.ai/workspace=true --overwrite
```
<Output>
<ExpectedOutput>
{`namespace/dev labeled`}
</ExpectedOutput>
</Output>

If you run it again, kubectl prints `namespace/dev not labeled`: the label is already there with the same value, so there was nothing to change. Either way, `dev` is labelled.

Without the label, the next step still succeeds, but every `sandbox create` in `dev` is refused:

```text
Error:   × code: 'The system is not in a state required for the operation's
  │ execution', message: "workspace 'dev' is not in the operator namespace
  │ allowlist"
```

</Step>

<Step n="3" title="Create the workspace in the gateway">

The namespace is where the sandboxes will **run**. This command makes the other half, the workspace's **record** in the gateway, which holds its providers, members and sandboxes. It doesn't create or change a namespace: in operator mode the gateway only uses a namespace with the same name, so name them alike:

```bash
openshell workspace create --name dev && openshell workspace list
```
<Output>
<ExpectedOutput>
{`✓ Created workspace dev
NAME     STATUS        CREATED               LABELS
default  Active        2026-11-11 11:41:33
lab      Active        2026-11-13 10:31:49
dev      Active        2026-11-13 10:33:06`}
</ExpectedOutput>
</Output>

You need both halves. Without this record, the gateway doesn't know `dev`, even though the namespace is labelled: `openshell --workspace dev provider create` fails with `workspace 'dev' not found`. Without the namespace and its label (steps 1 and 2), the record exists but every `sandbox create` is refused as `not in the operator namespace allowlist`.

From now on, `--workspace dev` on an `openshell` command acts on your workspace. Without it, commands act on `lab`, the default set for this shell (`OPENSHELL_WORKSPACE=lab`).

</Step>

<Step n="4" title="Add the litellm provider to your workspace">

`dev` has no providers yet. Create one with the same command the platform ran for `lab` (above), from the `litellm` profile already imported for every workspace: LiteLLM's key goes from its Secret into the `LITELLM_API_KEY` variable of this one command, and `--credential LITELLM_API_KEY` reads it from there, so it is never printed:

```bash
LITELLM_API_KEY="$(kubectl -n litellm get secret litellm-secrets -o jsonpath='{.data.LITELLM_MASTER_KEY}' | base64 -d)" openshell --workspace dev provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY && openshell --workspace dev provider list
```
<Output>
<ExpectedOutput>
{`✓ Created provider litellm
NAME     TYPE     CREDENTIAL_KEYS   CONFIG_KEYS
litellm  litellm  1                 0`}
</ExpectedOutput>
</Output>

</Step>

Now `dev` has its own `litellm` provider, stored by the gateway. Any sandbox you create in `dev` with `--provider litellm` gets a placeholder for it, as `agent-0` does in `lab`; the next sections show what that looks like.

</Section>

<Section n="3" title="What a sandbox sees: a placeholder that still works">

Your `dev` has no sandbox yet (that's 1.4), so look at `agent-0`, which `lab`'s `litellm` provider is attached to. See what that gave it, and use it.

<Step n="1" title="Read the key in agent-0's environment">

`agent-0` is the sandbox the platform created at setup (you listed it in [1.2](/learn/deploy)), with `--provider litellm`. `openshell sandbox exec -n agent-0 -- …` runs one command inside it. Print the variable the provider gave it:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'echo $LITELLM_API_KEY'
```
<Output>
<ExpectedOutput>
{`openshell:resolve:env:v1535812..._LITELLM_API_KEY`}
</ExpectedOutput>
</Output>

A placeholder. There is no key anywhere in the sandbox to steal.

</Step>

<Step n="2" title="Use the placeholder to list the models">

Now call LiteLLM with it, exactly as you did with the master key in 0.3:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -H "Authorization: Bearer $LITELLM_API_KEY" http://litellm.litellm.svc.cluster.local:4000/v1/models | head -c 300; echo'
```

LiteLLM answers with its model list, so it received the **real** key: the supervisor swapped it in on the way.

</Step>

<Step n="3" title="Ask the model one question">

Now ask the model one question, with the same placeholder in the `Authorization` header:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s http://litellm.litellm.svc.cluster.local:4000/v1/chat/completions -H "Authorization: Bearer $LITELLM_API_KEY" -H "Content-Type: application/json" -d "{\"model\":\"default\",\"messages\":[{\"role\":\"user\",\"content\":\"Say hello in five words.\"}]}" | grep -o "\"content\":\"[^\"]*\""'
```

</Step>

</Section>

<Section n="4" title="See what the placeholder can't be used for">

The provider's profile allows model calls only. Try something else with the same key.

<Step n="1" title="Try LiteLLM's admin API: refused at L7">

The same key would open LiteLLM's **admin API** (create keys, read spend). The profile doesn't allow it, so the supervisor refuses before anything leaves the sandbox:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -X POST -H "Authorization: Bearer $LITELLM_API_KEY" http://litellm.litellm.svc.cluster.local:4000/key/generate; echo'
```
<Output>
<ExpectedOutput>
{`{"error":"policy_denied","policy":"_provider_litellm","rule":"POST /key/generate","detail":"POST /key/generate not permitted by policy","layer":"l7",...}`}
</ExpectedOutput>
</Output>

</Step>

</Section>

## What you learned

<Learned next="/learn/build-an-agent" nextLabel="Bring up a sandboxed agent">

- **You add a provider per workspace** with `openshell provider create`, from a profile; the key goes in through an environment variable and is never printed.
- **A provider is a credential the gateway keeps**, an instance of a profile. `litellm` holds LiteLLM's key; its profile says which variable a sandbox gets and which requests may carry the key.
- **The sandbox holds a placeholder.** It still works: the supervisor puts the real key on allowed calls on the way out.
- **Everything else is refused at L7**, before any key is attached: the admin API never sees a request.

</Learned>
