An agent is only useful once it can think, so it needs a model. On this platform the agent calls **LiteLLM's own API** with a key it doesn't have: the sandbox holds a placeholder, and the supervisor puts the real key on the request, only for the model calls the platform allows.

<Section n="1" title="Your model and key" goal="See where the model and key are set, and check they work.">

<Step n="1" title="The settings in .env">

LiteLLM holds the upstream key and model for the whole cluster. On the VM, `~/openshell-on-k8s/.env`:

```bash-ref
MODEL_API_KEY=nvapi-your-key-here
MODEL_BASE_URL=https://integrate.api.nvidia.com/v1
MODEL_NAME=meta/llama-3.3-70b-instruct
```

`MODEL_BASE_URL` is any OpenAI-compatible endpoint, `MODEL_NAME` the model id it serves. LiteLLM also names it `default`, so agents can ask for `default` and stay unaware of which model that is. (Get a free `nvapi-…` key at [build.nvidia.com](https://build.nvidia.com).)

</Step>

<Step n="2" title="Check the key and URL">

To check the key and URL before you wire them in:

```bash
cd ~/openshell-on-k8s && set -a && . ./.env && set +a
curl -sS "$MODEL_BASE_URL/models" -H "Authorization: Bearer $MODEL_API_KEY" | grep -o '"id":"[^"]*"' | head -5
```

A list of ids means the key and URL work; **401** is a bad key.

</Step>

<Step n="3" title="Apply an edited .env">

After editing `.env`, apply it with the LiteLLM tag only (it can outrun the in-page Run button, so use the Cluster shell):

```bash-interactive
ANSIBLE_TAGS=litellm ./scripts/setup.sh
```

</Step>

</Section>

<Section n="2" title="The provider" goal="See what a sandbox is given for model access.">

<Step n="1" title="List the providers">

Model access is an OpenShell **provider** named `litellm`, created at provisioning:

```bash
openshell provider list
```
<Output>
<ExpectedOutput>
{`NAME     TYPE     CREDENTIAL_KEYS   CONFIG_KEYS
litellm  litellm  1                 0`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Read its profile">

Its type is a **provider profile**, the access contract: which variable the sandbox gets, where the credential may go, and which requests are allowed there:

```bash
openshell profile describe litellm
```
<Output>
<ExpectedOutput>
{`Credentials:
  api_key (required)
    Environment variables: LITELLM_API_KEY
    Authentication: bearer
    Header: authorization

Endpoints (declared policy):
  litellm.litellm.svc.cluster.local
    Ports: 4000
    Protocol: rest
    Access: custom rules
    Rules: 6 allow, 0 deny
    Enforcement: enforce`}
</ExpectedOutput>
</Output>

The six rules are model calls only: `GET /v1/models`, `POST /v1/chat/completions`, `/v1/completions`, `/v1/responses`, `/v1/embeddings`, `/v1/messages`. The file is `ansible/roles/10-cli_providers/files/litellm-profile.yaml`.

</Step>

</Section>

<Section n="3" title="What the agent sees" goal="Call the model from agent-0 with a key it doesn't hold.">

<Step n="1" title="A placeholder, not a key">

`agent-0` was created with `--provider litellm`. Look at its environment:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'echo $LITELLM_API_KEY'
```
<Output>
<ExpectedOutput>
{`openshell:resolve:env:v1535812..._LITELLM_API_KEY`}
</ExpectedOutput>
</Output>

A placeholder. There is no key anywhere in the sandbox to steal.

</Step>

<Step n="2" title="List the models">

Now use it:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -H "Authorization: Bearer $LITELLM_API_KEY" http://litellm.litellm.svc.cluster.local:4000/v1/models | head -c 300; echo'
```

LiteLLM answers with its model list, so it received the **real** key: the supervisor swapped it in on the way.

</Step>

<Step n="3" title="A chat completion">

And a one-line chat completion:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s http://litellm.litellm.svc.cluster.local:4000/v1/chat/completions -H "Authorization: Bearer $LITELLM_API_KEY" -H "Content-Type: application/json" -d "{\"model\":\"default\",\"messages\":[{\"role\":\"user\",\"content\":\"Say hello in five words.\"}]}" | grep -o "\"content\":\"[^\"]*\""'
```

</Step>

</Section>

<Section n="4" title="What the agent can't do with it" goal="See the admin API refused at L7.">

<Step n="1" title="Try to generate a key">

The same key would open LiteLLM's **admin API** (create keys, read spend). The profile doesn't allow it, so the supervisor refuses before anything leaves the sandbox:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -X POST -H "Authorization: Bearer $LITELLM_API_KEY" http://litellm.litellm.svc.cluster.local:4000/key/generate; echo'
```
<Output>
<ExpectedOutput>
{`{"error":"policy_denied","policy":"_provider_litellm","rule":"POST /key/generate","detail":"POST /key/generate not permitted by policy","layer":"l7",...}`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="5" title="Change the model later" goal="Know the one setting that picks the model.">

Everything funnels through LiteLLM, so the model is one setting: edit `MODEL_NAME` in `.env` and run `ANSIBLE_TAGS=litellm ./scripts/setup.sh`. The `default` alias follows it; sandboxes, providers and policies don't change.

</Section>

<Callout type="note" title="What changed from older OpenShell">
Earlier releases routed every sandbox through a managed endpoint, <code>inference.local</code>. OpenShell 0.1 removed it: a sandbox reaches a model only through a provider you attach to <em>that</em> sandbox, and the agent calls the model's own API. Access is per sandbox and explicit, and the provider's L7 rules define exactly which calls are allowed.
</Callout>
