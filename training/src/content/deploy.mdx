## How it was installed

When the VM first booted, Brev ran the Launchable's setup script. It wrote your values to `.env` and ran **`./scripts/setup.sh`**, which installs Ansible and runs one playbook, `ansible/site.yml`. Each **role** in `ansible/roles/` installs one piece, in order. The OpenShell parts:

| Role | Installs | How |
|---|---|---|
| `03-k3s` | Kubernetes (k3s v1.37), one node | the k3s installer |
| `04-agent_sandbox` | the **agent-sandbox controller** and its `Sandbox` CRD (`agents.x-k8s.io`), v1.0.10 | `kubectl apply -f https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.10/sandbox.yaml` |
| `05-litellm` | LiteLLM, with your model values ([0.3.2](/learn/cluster-and-model)) | Helm chart `oci://ghcr.io/berriai/litellm-helm` |
| `08b-cert_manager` | cert-manager and the lab CA, for the gateway's mTLS certificates | Helm chart `oci://quay.io/jetstack/charts/cert-manager` |
| `09-openshell_gateway` | the **OpenShell gateway** 0.1.7 in namespace `openshell`, published on NodePort 30808, and the lab operator's client certificate (`OU=operator`) | `helm upgrade --install openshell oci://ghcr.io/nvidia/openshell/helm-chart --version 0.1.7 -n openshell -f values.yaml …` |
| `10-cli_providers` | the **`openshell` CLI** v0.1.7, signed in to the gateway as the operator; the platform workspace `lab`; its `litellm` provider ([1.3](/learn/inference)) | the release binary; `kubectl label`, `helm install openshell-workspace`, `openshell workspace create`; `openshell provider create` |
| `16-sandboxes` | `agent-0`, the platform's first sandbox, in `lab` | `openshell sandbox create` |
| `15-console` | the **OpenShell Console** | its Helm chart, from the console's repository |
| `17-skill-registry` | a private npm registry (Verdaccio) for skills | a Deployment and Service |

Keycloak, Kyverno, Envoy Gateway and the monitoring stack have roles of their own. The gateway's Helm values (`ansible/roles/09-openshell_gateway/files/values.yaml`) choose how workspaces map to namespaces: **operator** mode, where each workspace is a namespace of the same name, prepared ahead of time with the `openshell-workspace` chart. Role `10-cli_providers` prepared the platform's own workspace, `lab`, that way, created its `litellm` provider, and made `lab` the default for `openshell` commands (`OPENSHELL_WORKSPACE=lab`). You'll make your own workspace in [1.4](/learn/build-an-agent).

To change a setting later, edit `.env` and re-run one role by its tag, for example `ANSIBLE_TAGS=litellm ./scripts/setup.sh`.

## OpenShell on Kubernetes

One VM runs the whole thing. From the bottom up, each layer hands a safer, more managed surface to the one above, until at the top you have an AI agent that can only do what your policy allows.

Scroll down to build one sandbox on Kubernetes in deployment order: LiteLLM, observability, Keycloak, the OpenShell chart, a workspace, then the sandbox. The agent reaches its model only through the supervisor and LiteLLM.

<ReadScene scene="k8s" />

You ask the gateway for a sandbox. It writes a `Sandbox` resource and starts a supervisor pod; the controller turns the resource into the workload pod running OpenClaw. The workload pod can only talk to its supervisor. When the agent calls LiteLLM, the supervisor checks the request against the sandbox's policy, swaps the placeholder in `Authorization` for the real key, and forwards it.

<Callout type="note" title="The mental model">
A sandbox is a pair of pods plus a policy. Creating an agent means creating a sandbox; deleting it tears both pods down. Everything else, isolation, policy, credentials and audit, hangs off that.
</Callout>

### Each component in a sentence

- **k3s**: single-node upstream Kubernetes. Lightweight, but a real cluster: the same CRDs, RBAC, NetworkPolicy and scheduler you'd use anywhere. The kubeconfig is `/etc/rancher/k3s/k3s.yaml`.
- **agent-sandbox controller**: [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox). It reconciles each `Sandbox` custom resource (`agents.x-k8s.io`) into a pod, the way a Deployment controller reconciles ReplicaSets.
- **OpenShell gateway** (namespace `openshell`): the control plane. It creates sandboxes, stores their policies and provider credentials, and decides who may do what. The CLI reaches it on NodePort **30808**.
- **Sandboxes** (one namespace per workspace, of the same name, e.g. `lab`): each one is **two pods**, the agent's workload pod and its supervisor pod. The supervisor owns the agent's network.
- **LiteLLM** (namespace `litellm`): one OpenAI-compatible endpoint in front of the model. Agents reach it through the `litellm` **provider**, with a key they never see.
- **Keycloak**, **Envoy Gateway** and the **OpenShell Console**: people sign in with Keycloak; Envoy publishes the training site, Keycloak and Grafana on one host and the console on its own.
- **Monitoring**: Prometheus and Grafana for metrics, Loki for logs and OpenShell's audit events, Tempo for traces.
- **OpenClaw 🦞**: the default agent, baked into the default sandbox image `ghcr.io/ansjindal/openshell-on-k8s/openclaw-sandbox`.


**Open the Cluster shell.** It's a real bash shell on the VM, with `KUBECONFIG` pointed at `/etc/rancher/k3s/k3s.yaml`, started in the repository folder.
