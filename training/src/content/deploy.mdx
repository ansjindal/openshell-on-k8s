## How it was installed

Nothing to run here: this happened once, when the VM first booted.

<Diagram id="install-flow" n="1.1" caption="One pipeline: the Launchable's values go into .env, setup.sh installs Ansible, and one playbook runs the roles in order." />

On the k3s cluster, the OpenShell pieces went in with these commands, in this order. The setup runs them through Ansible so they can be re-run safely, but each is an ordinary `kubectl`, `helm` or `openshell` command you could type yourself.

<Timeline>

<TStep n="1" title="The Sandbox controller">

The open-source agent-sandbox controller and its `Sandbox` resource, which OpenShell builds on.

```bash-ref
kubectl apply -f https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.10/sandbox.yaml
```

</TStep>

<TStep n="2" title="cert-manager">

Issues the certificates for the gateway's mTLS.

```bash-ref
helm upgrade --install cert-manager oci://quay.io/jetstack/charts/cert-manager --version v1.21.3 \
  --namespace cert-manager --create-namespace --set crds.enabled=true
```

</TStep>

<TStep n="3" title="LiteLLM, the model gateway">

With your model values from the Launchable ([0.3.2](/learn/cluster-and-model)).

```bash-ref
helm upgrade --install litellm oci://ghcr.io/berriai/litellm-helm --version 1.108.4 \
  --namespace litellm --create-namespace -f litellm-values.yaml
```

</TStep>

<TStep n="4" title="The OpenShell gateway">

NVIDIA's Helm chart, in namespace `openshell`, with `pi-sandbox` as the default sandbox image. Its settings are in [`values.yaml`](https://github.com/ansjindal/openshell-on-k8s/blob/main/ansible/roles/09-openshell_gateway/files/values.yaml): who may sign in, operator mode for workspaces, fail-closed policy loading.

```bash-ref
helm upgrade --install openshell oci://ghcr.io/nvidia/openshell/helm-chart --version 0.1.7 \
  --namespace openshell --create-namespace -f values.yaml \
  --set sandbox.image.repository=ghcr.io/ansjindal/openshell-on-k8s/pi-sandbox --set-string sandbox.image.tag=1.5.2
```

</TStep>

<TStep n="5" title="The openshell CLI">

Downloaded from the release, and signed in to the gateway as the lab operator.

```bash-ref
curl -fsSLO https://github.com/NVIDIA/OpenShell/releases/download/v0.1.7/openshell-x86_64-unknown-linux-musl.tar.gz
tar -xzf openshell-x86_64-unknown-linux-musl.tar.gz openshell && sudo install -m 0755 openshell /usr/local/bin/
openshell gateway add https://localhost:30808 --local --name fleet
```

</TStep>

<TStep n="6" title="The platform's workspace, lab">

NVIDIA's `openshell-workspace` chart in a new namespace, the label that lets the gateway use it, the workspace in the gateway, then its `litellm` provider. You'll do the same for your own workspace in [1.3](/learn/inference).

```bash-ref
helm upgrade --install openshell-workspace oci://ghcr.io/nvidia/openshell/openshell-workspace --version 0.1.7 --namespace lab --create-namespace
kubectl label namespace lab openshell.ai/workspace=true
openshell workspace create --name lab
openshell profile import -f litellm-profile.yaml --global
openshell --workspace lab provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY
```

</TStep>

<TStep n="7" title="The first sandbox and the Console">

`agent-0` in `lab`, and the OpenShell Console from its repository ([github.com/ai-openshell/console](https://github.com/ai-openshell/console)).

```bash-ref
openshell --workspace lab sandbox create --name agent-0 --provider litellm \
  --policy manifests/policies/baseline.yaml --memory 3Gi --no-tty --detach -- sleep infinity
helm upgrade --install openshell-dashboard ./openshell-console/deploy/helm/openshell-dashboard \
  --namespace openshell -f console-values.yaml
```

</TStep>

</Timeline>

Keycloak, Envoy Gateway, Kyverno and the monitoring stack went in the same way, each with its own Helm chart; the skill repository and the MCP server for Module 3 with `kubectl apply`.

<Callout type="tip" title="Changing a setting later">
Edit <code>.env</code> and re-run only the role that needs it, by its tag: for example <code>ANSIBLE_TAGS=litellm ./scripts/setup.sh</code>.
</Callout>

## What a workspace is

Step 6 made a **workspace**, OpenShell's tenant. It has two halves: a record in the gateway (its providers, its members, and its sandboxes with their policies) and, in operator mode, a Kubernetes namespace of the same name, where those sandboxes actually run. The setup also made `lab` the default for `openshell` commands (`OPENSHELL_WORKSPACE=lab`); you'll make your own workspace in [1.3](/learn/inference).

## The platform, piece by piece

One VM runs the whole thing. From the bottom up, each layer hands a safer, more managed surface to the one above, until at the top you have an agent that can only do what your policy allows.

<Callout type="note" title="The mental model">
A sandbox is a pair of pods plus a policy. You ask the gateway for one; it writes a <code>Sandbox</code> resource and starts a supervisor pod, and the controller turns the resource into the workload pod running the agent. The workload pod can only talk to its supervisor, which checks every request against the policy and adds the real key only to allowed model calls. Deleting the sandbox tears both pods down.
</Callout>

**Open the Cluster shell.** It's a real bash shell on the VM, with `KUBECONFIG` pointed at `/etc/rancher/k3s/k3s.yaml`, started in the repository folder.

<Section n="1" title="Check the OpenShell control plane pods">

OpenShell's control plane lives in namespace `openshell`: the gateway and the Console.

```bash
kubectl -n openshell get pods
```

</Step>

</Section>

<Section n="2" title="Check that the CLI reaches the gateway, and who you are to it">

The `openshell` CLI talks only to the gateway. Check that it's connected, and ask the gateway who it thinks you are.

<Step n="1" title="Ask the gateway for its status">

The CLI reaches the gateway on NodePort `30808`. Ask it for its status:

```bash
openshell status
```
<Output>
<ExpectedOutput>
{`Server Status

  Gateway: fleet
  Server: https://localhost:30808
  Status: Connected
  Authentication: Authenticated (mTLS transport)
  Version: 0.1.7`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Ask the gateway who you are">

The gateway accepts no anonymous calls. Ask it who it thinks you are:

```bash
openshell whoami
```
<Output>
<ExpectedOutput>
{`Current User

  Subject: lab-operator
  Name: lab-operator
  Provider: mtls
  Roles: operator`}
</ExpectedOutput>
</Output>

This shell presents a client certificate with `OU=operator`, which cert-manager issued for the VM. An operator is a platform admin across every workspace. People in the browser sign in with Keycloak instead; you'll meet them in [2.4 The OpenShell Console](/learn/console).

</Step>

</Section>

<Section n="3" title="Find agent-0, the sandbox the setup created">

<Section n="4" title="Check that LiteLLM and Keycloak are running">

LiteLLM is the model gateway you met in 0.3. **Keycloak** is the lab's sign-in for **people**: it holds the users (`demo`, `learner`), their passwords and their roles. OpenShell never sees a password: the Console sends you to Keycloak, Keycloak gives you a signed token, and the gateway checks that token on every call. The lab's own CLI doesn't use Keycloak at all: it presents a client certificate.
