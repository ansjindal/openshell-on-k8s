## How it was installed

Nothing to run here: this happened once, when the VM first booted.

<Diagram id="install-flow" n="1.1" caption="One pipeline: the Launchable's values go into .env, setup.sh installs Ansible, and one playbook runs the roles in order." />

On the k3s cluster, the OpenShell pieces went in with these commands, in this order. The setup runs them through Ansible so they can be re-run safely, but each one is an ordinary `kubectl` or `helm` command you could type yourself.

**1. The Sandbox controller.** The open-source agent-sandbox controller and its `Sandbox` resource, which OpenShell builds on:

```bash-ref
kubectl apply -f https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.10/sandbox.yaml
```

**2. cert-manager**, which issues the certificates for the gateway's mTLS:

```bash-ref
helm upgrade --install cert-manager oci://quay.io/jetstack/charts/cert-manager --version v1.21.3 \
  --namespace cert-manager --create-namespace --set crds.enabled=true
```

**3. LiteLLM**, the model gateway, with your model values from the Launchable ([0.3.2](/learn/cluster-and-model)):

```bash-ref
helm upgrade --install litellm oci://ghcr.io/berriai/litellm-helm --version 1.108.4 \
  --namespace litellm --create-namespace -f litellm-values.yaml
```

**4. The OpenShell gateway**, NVIDIA's Helm chart, in namespace `openshell`:

```bash-ref
helm upgrade --install openshell oci://ghcr.io/nvidia/openshell/helm-chart --version 0.1.7 \
  --namespace openshell --create-namespace -f ansible/roles/09-openshell_gateway/files/values.yaml \
  --set sandbox.image.repository=ghcr.io/ansjindal/openshell-on-k8s/pi-sandbox --set-string sandbox.image.tag=1.5.2
```

`--set sandbox.image…` makes `pi-sandbox` the image every sandbox starts from unless it says otherwise. Everything else is in the values file (plus small overlays for Keycloak, mTLS and tracing):

<YamlRead id="gateway-values" />

**5. The `openshell` CLI**, signed in to the gateway as the lab operator:

```bash-ref
curl -fsSLO https://github.com/NVIDIA/OpenShell/releases/download/v0.1.7/openshell-x86_64-unknown-linux-musl.tar.gz
tar -xzf openshell-x86_64-unknown-linux-musl.tar.gz openshell && sudo install -m 0755 openshell /usr/local/bin/
openshell gateway add https://localhost:30808 --local --name fleet
```

**6. The platform's workspace, `lab`, with its model provider.** A labelled namespace, NVIDIA's `openshell-workspace` chart in it, the workspace in the gateway, then the `litellm` provider ([1.3](/learn/inference)):

```bash-ref
kubectl create namespace lab && kubectl label namespace lab openshell.ai/workspace=true
helm upgrade --install openshell-workspace oci://ghcr.io/nvidia/openshell/openshell-workspace --version 0.1.7 --namespace lab
openshell workspace create --name lab
openshell profile import -f litellm-profile.yaml --global
openshell --workspace lab provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY
```

**7. The first sandbox and the Console.** `agent-0` in `lab`, and the OpenShell Console from its repository ([github.com/ai-openshell/console](https://github.com/ai-openshell/console)):

```bash-ref
openshell --workspace lab sandbox create --name agent-0 --provider litellm \
  --policy manifests/policies/baseline.yaml --memory 3Gi --no-tty --detach -- sleep infinity
helm upgrade --install openshell-dashboard ./openshell-console/deploy/helm/openshell-dashboard \
  --namespace openshell -f console-values.yaml
```

Keycloak, Envoy Gateway, Kyverno and the monitoring stack went in the same way, each with its own Helm chart; the skill repository and the MCP server for Module 3 with `kubectl apply`.

<Callout type="note" title="Workspaces are namespaces">
In <strong>operator mode</strong> each workspace is a namespace of the same name, prepared ahead of time with the <code>openshell-workspace</code> chart, as in step 6. The setup also made <code>lab</code> the default for <code>openshell</code> commands (<code>OPENSHELL_WORKSPACE=lab</code>). You'll make your own in <a href="/learn/build-an-agent">1.4</a>.
</Callout>

<Callout type="tip" title="Changing a setting later">
Edit <code>.env</code> and re-run only the role that needs it, by its tag: for example <code>ANSIBLE_TAGS=litellm ./scripts/setup.sh</code>.
</Callout>

## The platform, piece by piece

One VM runs the whole thing. From the bottom up, each layer hands a safer, more managed surface to the one above, until at the top you have an agent that can only do what your policy allows.

### Each component in a sentence

- **k3s**: single-node upstream Kubernetes. Lightweight, but a real cluster: the same CRDs, RBAC, NetworkPolicy and scheduler you'd use anywhere. The kubeconfig is `/etc/rancher/k3s/k3s.yaml`.
- **agent-sandbox controller**: [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox). It reconciles each `Sandbox` custom resource (`agents.x-k8s.io`) into a pod, the way a Deployment controller reconciles ReplicaSets.
- **OpenShell gateway** (namespace `openshell`): the control plane. It creates sandboxes, stores their policies and provider credentials, and decides who may do what. The CLI reaches it on NodePort **30808**.
- **Sandboxes** (one namespace per workspace, of the same name, e.g. `lab`): each one is **two pods**, the agent's workload pod and its supervisor pod. The supervisor owns the agent's network.
- **LiteLLM** (namespace `litellm`): one OpenAI-compatible endpoint in front of the model. Agents reach it through the `litellm` **provider**, with a key they never see.
- **Keycloak**, **Envoy Gateway** and the **OpenShell Console**: people sign in with Keycloak; Envoy publishes the training site, Keycloak and Grafana on one host and the console on its own.
- **Monitoring**: Prometheus and Grafana for metrics, Loki for logs and OpenShell's audit events, Tempo for traces.
- **pi**: the agent, baked into the default sandbox image `ghcr.io/ansjindal/openshell-on-k8s/pi-sandbox` and already pointed at LiteLLM.

<Callout type="note" title="The mental model">
A sandbox is a pair of pods plus a policy. You ask the gateway for one; it writes a <code>Sandbox</code> resource and starts a supervisor pod, and the controller turns the resource into the workload pod running the agent. The workload pod can only talk to its supervisor, which checks every request against the policy and adds the real key only to allowed model calls. Deleting the sandbox tears both pods down.
</Callout>

**Open the Cluster shell.** It's a real bash shell on the VM, with `KUBECONFIG` pointed at `/etc/rancher/k3s/k3s.yaml`, started in the repository folder.

<Step n="2" title="Ask who you are">

The gateway accepts no anonymous calls. Ask it who you are:

```bash
openshell whoami
```
<Output>
<ExpectedOutput>
{`Current User

  Subject: lab-operator
  Name: lab-operator
  Provider: mtls
  Roles: operator`}
</ExpectedOutput>
</Output>

This shell presents a client certificate with `OU=operator`, which cert-manager issued for the VM. An operator is a platform admin across every workspace. People in the browser sign in with Keycloak instead; you'll meet them in [Users, Roles & Workspaces](/learn/access-control).

</Step>

</Section>
