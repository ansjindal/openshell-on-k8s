<Section n="1" title="How the conductor runs an investigation">

A fleet of specialists isn't useful until something *combines* them. That's a small **orchestrator** built into this page — no separate app. When you hit **Investigate**, it:

1. **Dispatches**: hands each specialist the tool call for its signal and runs pi in its sandbox, so the work happens **inside the agent's seal**, with only the tools its policy allows.
2. **Reads, for real**: each agent calls its **sre-tools** tool (`logs`→`loki_query`, `metrics`→`prometheus_query`, `traces`→`tempo_search`, `events`→`cluster_events` and `pod_status`) through the supervisor, and interprets the result with the platform skills.
3. **Concludes**: hands all the findings to the **analyst** agent (no tools), which reasons over them into a root cause **and a recommended remediation**.

You see **every agent's findings** *and* the analyst's concluded verdict — transparent, not a black box. The conductor never touches a backend itself; the agents do the governed reads. Watch the audit trail while it runs (`openshell logs <agent>` or Grafana, see [The Audit Trail](/learn/audit)): each agent, its one allowed host, every call logged.

<Callout type="note" title="Why MCP tools, not raw HTTP">
The agents never get a URL to Loki or Prometheus, and no network rule to reach them. They call named tools on the sre-tools MCP server, and each agent's policy names the tools it may call. The server holds the access; the policy decides who may use which tool; the audit log records every call.
</Callout>

</Section>

<Section n="2" title="The demo shop you will break">

<DemoArchitecture />

A continuous **loadgen** drives the instrumented **shop-app**, which on every checkout makes a real HTTP call to its **`payments`** dependency — and emits all three signals into the cluster's observability stack: **traces** → Tempo (OTLP), **metrics** → Prometheus (a ServiceMonitor scrapes `/metrics`), and **logs** → Loki (Grafana Alloy ships its stdout). A **kubernetes-event-exporter** feeds k8s events into Loki too. The sealed fleet reads those backends — so when `payments` goes down, it shows up across every signal at once, and the live traffic numbers (below) move in real time.

</Section>

<Section n="3" title="Break the shop, let the fleet investigate, approve the fix">

<IncidentLab />

<Step n="1" title="Deploy the demo shop">

**Deploy** stands up `shop-app` (a small instrumented service) plus a **loadgen** that drives it continuously — so the **live traffic numbers** (success/s, errors/s, error rate) and the logs/metrics/traces are always real.

</Step>

<Step n="2" title="Inject a fault: take payments down">

**Inject fault** takes a **real dependency down**: `kubectl scale deploy/payments --replicas=0`. shop-app's checkout makes a real HTTP call to `payments` on every request — with payments gone, those calls genuinely fail (connection refused) and checkout returns **503**. Nothing artificial; watch the payments pod terminate and the **error rate climb to 100%**.

</Step>

<Step n="3" title="Let the fleet investigate">

**Investigate** runs the fleet against the live telemetry: `metrics` sees the 5xx spike, `logs` sees the `checkout failed: payment call failed…` lines, `traces` sees the failing `charge-payment` span, and **`events` sees the smoking gun** — `payments` was scaled to 0 right as the errors began. The analyst asks *"what changed?"* and pins it on the dependency outage.

</Step>

<Step n="4" title="Approve and apply the fix">

**Your fix** is the human-approved remediation — a **real fix**: `kubectl scale deploy/payments --replicas=1`, bringing the dependency back. Watch the error rate fall to 0. Applying it is the one step a human owns.

</Step>

<Callout type="note" title="What “Inject fault” actually does — a real dependency outage">
No simulated flag. <strong>Inject fault</strong> runs <code>kubectl scale deploy/payments --replicas=0</code> —
it genuinely takes shop-app's <code>payments</code> dependency offline. shop-app calls
<code>payments</code> over HTTP on every checkout, so with it gone those calls fail with a real
<strong>connection refused</strong> and checkout returns 503. The failure <em>emerges</em> from a
real broken dependency — exactly like a real outage. The fleet sees it in metrics (5xx), logs
("payment call failed…"), traces (failing <code>charge-payment</code> span), and decisively in
<strong>events</strong> (<code>payments scaled to 0</code>). <strong>Apply remediation</strong> is
the real fix: <code>kubectl scale deploy/payments --replicas=1</code>. A real problem, diagnosed
from real telemetry, fixed by a real change.
</Callout>

</Section>

<Section n="4" title="Agents recommend; humans decide">

The agents never touch the cluster — they're sealed from the Kubernetes API and only *read* telemetry. They produce a **recommendation**; the human approves (and may change) the **actual** change. That gap between "what the fleet suggested" and "what you applied" is the human-in-the-loop, made explicit and on the record.

<Callout type="rh" title="Manual here, ArgoCD in production">
In this lab the approved remediation clears the injected fault behind a confirm. In production it's a <strong>git revert</strong> a reviewer approves and <strong>ArgoCD</strong> syncs — same shape (fleet recommends → human approves → delivered), just GitOps delivery. The fleet's job, and the human gate, are identical.
</Callout>

<Callout type="note" title="Make the incident harder">
The payment-503 fault is the clean demo (and there's a <code>latency</code> fault too). For a harder exercise, inject something the four signals must <em>combine</em> to explain — slow spans in <code>traces</code>, an SLO breach in <code>metrics</code>, errors in <code>logs</code> — and watch the analyst reconcile all four, then recommend the remediation you approve.
</Callout>

</Section>

That's the capstone: a governed, observable SRE copilot — spun up repeatably, each agent provably bounded, investigating from this page, and kept honest by a human on the only step that changes the world.
