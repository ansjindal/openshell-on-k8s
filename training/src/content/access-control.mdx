So far you've been the **operator**: this shell's client certificate makes you a platform admin. Real people sign in with **Keycloak**, and what they can do comes from two things: their **role** in the token, and the **workspaces** they're members of.

<BeforeYouStart
  will="sign in as a standard user who sees nothing, create a workspace, add that user to it, give it model access and a sandbox, then clean up."
  time="about fifteen minutes."
/>

<Section n="1" title="Meet two people with two different roles" goal="Meet the two Keycloak users and their roles.">

<Step n="1" title="Get demo's and learner's passwords">

The realm `openshell` has two users. Their passwords were generated at provisioning:

```bash
grep -E 'KC_(DEMO|LEARNER)_PASSWORD' .sso-secrets.env
```

| User | Keycloak realm role | In OpenShell |
|---|---|---|
| `demo` | `openshell-admin` | **Platform admin**: every workspace, gateway settings, the global policy |
| `learner` | `openshell-user` | **Standard user**: only the workspaces they're a member of |

The gateway reads the roles from the token's `realm_access.roles` claim.

</Step>

</Section>

<Section n="2" title="Sign in as learner and see what a user can do" goal="See that a user with no workspace sees nothing.">

<Step n="1" title="Open the console as learner">

Open the **OpenShell Console** (header link, or `https://console-<brevid>.<domain>`) in a private window and sign in as `learner`. You'll see:

```bash-ref
Role: Standard user
Workspaces: No workspaces. Ask a platform admin to add you to a workspace.
```

`learner` can sign in but sees nothing: there is no workspace they belong to.

</Step>

<Step n="2" title="Try the lab workspace as learner: refused">

Try opening `…/workspaces/lab` directly; the gateway refuses with *not a member of workspace 'lab'*. The console only displays what the gateway allows.

</Step>

</Section>

<Section n="3" title="Create the team-a workspace and add learner to it" goal="Create team-a and make learner a member.">

<Step n="1" title="Create team-a: namespace, chart and workspace">

A **workspace** is a tenant: its own sandboxes, providers and members. Make `team-a` the way you made `dev` in [1.4](/learn/build-an-agent): a namespace labelled as a workspace, the `openshell-workspace` chart in it, then the workspace in the gateway:

```bash
kubectl create namespace team-a --dry-run=client -o yaml | kubectl apply -f - && kubectl label namespace team-a openshell.ai/workspace=true --overwrite && helm upgrade --install openshell-workspace oci://ghcr.io/nvidia/openshell/openshell-workspace --version 0.1.7 --namespace team-a --wait | grep STATUS && openshell workspace create --name team-a
```
<Output>
<ExpectedOutput>
{`namespace/team-a created
namespace/team-a labeled
STATUS: deployed
✓ Created workspace team-a`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Add learner as a member, by subject">

Members are identified by their OIDC **subject** (the token's `sub`, Keycloak's user id), not their name. Look it up and add `learner` as a user:

```bash
SUB=$(./scripts/keycloak-user-id.sh learner) && openshell workspace member add --workspace team-a --subject "$SUB" --role user && openshell workspace member list --workspace team-a
```
<Output>
<ExpectedOutput>
{`✓ Added fadec839-948e-4ab0-913c-0c64ca8f3f12 to workspace team-a as user
SUBJECT                               ROLE
fadec839-948e-4ab0-913c-0c64ca8f3f12  user`}
</ExpectedOutput>
</Output>

(In the console, `demo` can do the same: **Workspaces → Create workspace**, then **Members → Add member**. A signed-in user finds their own subject under **Copy my subject ID** in the user menu.)

</Step>

</Section>

<Section n="4" title="Give team-a its own model provider" goal="Create team-a's own litellm provider.">

<Step n="1" title="Create team-a's litellm provider">

Providers belong to a workspace. `team-a` needs its own `litellm` provider (the profile is platform-wide, so it can be reused):

```bash
LITELLM_API_KEY="$(kubectl -n litellm get secret litellm-secrets -o jsonpath='{.data.LITELLM_MASTER_KEY}' | base64 -d)" openshell --workspace team-a provider create --name litellm --type litellm --global-profile --credential LITELLM_API_KEY
```
<Output>
<ExpectedOutput>
{`✓ Created provider litellm`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="5" title="Let learner work in team-a" goal="Give learner a sandbox and see the tenant boundary.">

<Step n="1" title="Create a sandbox in team-a">

Refresh the console as `learner`: **team-a** is there. Create a sandbox in it from the console (**Create sandbox**, attach provider `litellm`), or from here on their behalf:

```bash
openshell --workspace team-a sandbox create --name lab-a --provider litellm --policy manifests/policies/baseline.yaml --no-tty --detach -- sleep infinity && openshell --workspace team-a sandbox list
```
<Output>
<ExpectedOutput>
{`NAME   CREATED              PHASE
lab-a  2026-11-13 10:35:47  Ready`}
</ExpectedOutput>
</Output>

`learner` sees `lab-a`, its policy revision and its providers, and can open its logs and terminal. They still can't see `agent-0`: it's in `lab`.

</Step>

<Step n="2" title="See one namespace per workspace">

```bash
kubectl get namespaces -l openshell.ai/workspace=true && kubectl -n team-a get pods
```
<Output>
<ExpectedOutput>
{`NAME     STATUS   AGE
dev      Active   2m54s
lab      Active   4m12s
team-a   Active   13s
NAME                                                 READY   STATUS    RESTARTS   AGE
lab-a                                                1/1     Running   0          12s
os-supervisor-9c0f9e48-a1ef-44c6-8641-fb1e6b318c70   1/1     Running   0          12s`}
</ExpectedOutput>
</Output>

Each workspace is its own namespace, of the same name (`workspaceMode: operator`): `lab` for the platform, `dev` from 1.4, `team-a` here. Sandboxes of one workspace can't land in another's namespace, and the chart's RBAC lets the gateway work only in namespaces you prepared.

</Step>

</Section>

<Section n="6" title="Remove team-a again" goal="Remove the sandbox, provider and workspace.">

<Step n="1" title="Delete team-a's sandbox, provider, workspace and namespace">

```bash
openshell --workspace team-a sandbox delete lab-a && openshell --workspace team-a provider delete litellm && openshell workspace delete team-a && helm uninstall openshell-workspace -n team-a && kubectl delete namespace team-a
```

</Step>

</Section>

<Callout type="nv" title="Same rules for every door">
The CLI, the console and the SDKs all call the same gateway, and the gateway checks every call against the caller's identity, role and workspace membership. The console holds no privileges of its own: it forwards the signed-in user's token.
</Callout>
