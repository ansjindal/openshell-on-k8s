You have sealed an agent, given it credentials it never sees and a persona. Time to put agents to work: the **fleet helper** creates several sandboxes at once and hands a prompt to one agent or the whole fleet.

/>

<Section n="1" title="Meet the fleet helper and bring up two agents">

<Step n="1" title="What the fleet helper does">

Running one agent, you used `openshell` directly. For several at once, the lab has a helper: `./scripts/fleet` is a thin wrapper around the same `openshell sandbox create`, `exec` and `logs` commands, for a fleet of sandboxes named `agent-0`, `agent-1`, …:

```bash-ref
fleet up [N]                          # create sandboxes agent-0 … agent-(N-1)
fleet down                            # delete every fleet sandbox
fleet status                          # sandboxes + the pods behind them
fleet task "<prompt>" [agent-i|all]   # run a prompt across the fleet, in parallel
fleet shell <agent-i>                 # interactive shell inside one sandbox
fleet logs <agent-i>                  # OpenShell logs for one sandbox
```

`fleet up` runs, for each new agent, the same `openshell sandbox create` you used in [1.4](/learn/build-an-agent), with `--provider litellm`, the baseline policy and `--memory 3Gi`. The agent in each sandbox is **pi**, which the sandbox image ships already pointed at LiteLLM; `fleet task` runs `pi --no-session -p "<prompt>"` in each one.

</Step>

<Step n="2" title="Check which agents are running">

```bash
./scripts/fleet status
```

</Step>

<Section n="2" title="Send one task to every agent" goal="Fan one prompt out to every agent.">

<Step n="1" title="Send a haiku task to all agents">

`fleet task` takes a prompt and an optional target. `all` fans it out to every agent:

```bash
./scripts/fleet task "Write a haiku about Kubernetes pods" all
```
<Output summary="Two agents, two haikus, in parallel.">
<ExpectedOutput>
{`Running pi on 2 agent(s) in parallel...

── [agent-1] ───────────────
Containers awake
In the cluster's gentle hum
Pods rest, scale, and sleep

── [agent-0] ───────────────
Containers at rest
Pods hold containers tight so
Cluster hums soft low

All agents finished.`}
</ExpectedOutput>
</Output>

Each agent receives the prompt, calls LiteLLM through its `litellm` provider (the supervisor injects the key), and works on it independently in its own sandbox.

</Step>

</Section>

<Section n="3" title="Send a task to one agent" goal="Send a task to just one agent.">

<Step n="1" title="Ask agent-0 alone">

Drop `all` (or name an agent) to send the task to just one:

```bash
./scripts/fleet task "List three reasons to sandbox an AI agent" agent-0
```
<Output>
<ExpectedOutput>
{`── [agent-0] ───────────────

`agent-0` answered as **Sandy** if you gave it the persona in the last lesson: `fleet task` runs the same pi, with the same `~/.pi/agent/AGENTS.md`.

</Step>

</Section>

<Section n="4" title="Read what the logs recorded" goal="See the output and the agent's reasoning.">

<Step n="1" title="Follow the sandbox's OpenShell log">

`fleet logs` follows the sandbox's OpenShell log (press **Ctrl-C** to stop). Each task shows up as the model call its supervisor allowed:

```bash-interactive
./scripts/fleet logs agent-0
```

```text
[1794571139.838] [sandbox] [OCSF ] [ocsf] NET:OPEN [INFO] ALLOWED /usr/bin/node(0) -> litellm.litellm.svc.cluster.local:4000 [policy:_provider_litellm engine:opa]
[1794571139.846] [sandbox] [OCSF ] [ocsf] HTTP:POST [INFO] ALLOWED POST http://litellm.litellm.svc.cluster.local:4000/v1/chat/completions [policy:_provider_litellm engine:l7]
```

</Step>

<Step n="2" title="Read the workload pod's own log">

The workload pod's own log is the sandbox runtime's: its network broker and seccomp notices, not the agent's answers (those came back through `fleet task`):

```bash
kubectl -n lab logs agent-0
```

<ExpectedOutput>

</Output>

</Step>

<Section n="5" title="Watch the whole fleet with status" goal="Get the bird's-eye view while agents run.">

<Step n="1" title="Show the fleet's status">

With multiple agents on one prompt, `status` gives you the bird's-eye view while they run:

```bash
./scripts/fleet status
```

</Step>

<Callout type="lab" title="This is the payoff">
Each task ran inside its own sandbox, reached the model without ever holding the key, and was bounded by the sandbox's policy. That's the entire point of the stack — useful, autonomous, and contained — demonstrated in one command.
</Callout>

Keep the fleet up — it's what the rest of the course (the console, [the Module 4 capstone](/learn/m4-overview)) drives too. `./scripts/fleet down` is for when you're done with the whole launchable, not this lesson.

## What you learned

- **Target a single agent.** Send a task to just one agent.
- **Read the logs.** See the output and the agent's reasoning.
- **Watch the whole fleet work.** Get the bird's-eye view while agents run.
