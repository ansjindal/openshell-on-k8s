You have an isolated agent that can reach a model. Time to put it to work. The fleet helper lets you hand a prompt to one agent or the whole fleet at once.

<BeforeYouStart
  will="check the fleet, hand a prompt to every agent and to one agent, and read what they did."
  time="about five minutes. Each step has a Run button that runs its command on your lab VM."
/>

<Section n="1" title="Make sure you have agents" goal="Have at least one agent running.">

<Step n="1" title="Check the fleet">

```bash
./scripts/fleet status
```

</Step>

<Step n="2" title="Bring some up if needed">

If the list is empty, bring some up:

```bash
./scripts/fleet up 2
```

</Step>

</Section>

<Section n="2" title="Hand the fleet a task" goal="Fan one prompt out to every agent.">

<Step n="1" title="Send to all">

`fleet task` takes a prompt and an optional target. `all` fans it out to every agent:

```bash
./scripts/fleet task "Write a haiku about Kubernetes pods" all
```

Each agent receives the prompt, calls LiteLLM through its `litellm` provider (the supervisor injects the key), and works on it independently in its own sandbox.

</Step>

</Section>

<Section n="3" title="Target a single agent" goal="Send a task to just one agent.">

<Step n="1" title="Send to agent-0">

Drop `all` (or name an agent) to send the task to just one:

```bash
./scripts/fleet task "List three reasons to sandbox an AI agent" agent-0
```

</Step>

</Section>

<Section n="4" title="Read the logs" goal="See the output and the agent's reasoning.">

<Step n="1" title="Fleet logs">

The output and the agent's reasoning show up in its logs:

```bash
./scripts/fleet logs agent-0
```

</Step>

<Step n="2" title="The raw pod logs">

That's the same as reading the pod's logs directly, if you prefer the raw view:

```bash
kubectl -n openshell-lab-default logs agent-0
```

</Step>

</Section>

<Section n="5" title="Watch the whole fleet work" goal="Get the bird's-eye view while agents run.">

<Step n="1" title="Fleet status">

With multiple agents on one prompt, `status` gives you the bird's-eye view while they run:

```bash
./scripts/fleet status
```

</Step>

</Section>

<Callout type="lab" title="This is the payoff">
Each task ran inside its own sandbox, reached the model without ever holding the key, and was bounded by the sandbox's policy. That's the entire point of the stack — useful, autonomous, and contained — demonstrated in one command.
</Callout>

Keep the fleet up — it's what the rest of the course (the console, [Part III](/learn/what-youll-build)) drives too. `./scripts/fleet down` is for when you're done with the whole launchable, not this lesson.
