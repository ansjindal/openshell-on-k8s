You have sealed an agent, given it a persona and skills. Time to put agents to work: the **fleet helper** creates several sandboxes at once and hands a prompt to one agent or the whole fleet.

<Section n="1" title="Meet the fleet helper, and make sure you have agents">

<Step n="1" title="What the fleet helper does">

Running one agent, you used `openshell` directly. For several at once, the lab has a helper: `./scripts/fleet` is a thin wrapper around the same `openshell sandbox create`, `exec` and `logs` commands, for a fleet of sandboxes named `agent-0`, `agent-1`, …:

```bash-ref
fleet up [N]                          # create sandboxes agent-0 … agent-(N-1)
fleet down                            # delete every fleet sandbox
fleet status                          # sandboxes + the pods behind them
fleet task "<prompt>" [agent-i|all]   # run a prompt across the fleet, in parallel
fleet shell <agent-i>                 # interactive shell inside one sandbox
fleet logs <agent-i>                  # OpenShell logs for one sandbox
```

`fleet up` runs, for each new agent, the same `openshell sandbox create` you used in [1.4](/learn/build-an-agent), with `--provider litellm`, the baseline policy and `--memory 3Gi` (one OpenClaw turn peaks near 2 GB). The agent in each sandbox is **OpenClaw**, the default image's agent.

</Step>

<Step n="2" title="Check the fleet">

```bash
./scripts/fleet status
```

</Step>

<Step n="3" title="Bring the fleet to two">

`agent-0` was made at setup. Add a second agent, `agent-1` (an agent that already exists is left alone):

```bash
./scripts/fleet up 2
```

<Section n="2" title="Hand the fleet a task" goal="Fan one prompt out to every agent.">

<Step n="1" title="Send to all">

`fleet task` takes a prompt and an optional target. `all` fans it out to every agent:

```bash
./scripts/fleet task "Write a haiku about Kubernetes pods" all
```

Each agent receives the prompt, calls LiteLLM through its `litellm` provider (the supervisor injects the key), and works on it independently in its own sandbox.

</Step>

</Section>

<Section n="3" title="Target a single agent" goal="Send a task to just one agent.">

<Step n="1" title="Send to agent-0">

Drop `all` (or name an agent) to send the task to just one:

```bash
./scripts/fleet task "List three reasons to sandbox an AI agent" agent-0
```

</Step>

</Section>

<Section n="4" title="Read the logs" goal="See the output and the agent's reasoning.">

<Step n="1" title="Fleet logs">

The output and the agent's reasoning show up in its logs:

```bash
./scripts/fleet logs agent-0
```

</Step>

<Step n="2" title="The raw pod logs">

That's the same as reading the pod's logs directly, if you prefer the raw view:

```bash
kubectl -n lab logs agent-0
```

</Step>

</Section>

<Section n="5" title="Watch the whole fleet work" goal="Get the bird's-eye view while agents run.">

<Step n="1" title="Fleet status">

With multiple agents on one prompt, `status` gives you the bird's-eye view while they run:

```bash
./scripts/fleet status
```

</Step>

</Section>

<Callout type="lab" title="This is the payoff">
Each task ran inside its own sandbox, reached the model without ever holding the key, and was bounded by the sandbox's policy. That's the entire point of the stack — useful, autonomous, and contained — demonstrated in one command.
</Callout>

Keep the fleet up — it's what the rest of the course (the console, [the Module 3 capstone](/learn/m4-overview)) drives too. `./scripts/fleet down` is for when you're done with the whole launchable, not this lesson.
