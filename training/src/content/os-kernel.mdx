An agent is, by design, an untrusted process you've given a shell and a network. OpenShell holds it in with layers, so that defeating any single one doesn't get an attacker much. This chapter is the inner layers: what the kernel lets the agent's process touch, and the Kubernetes guardrails around its pod. Then you test them from inside.

## The workload pod: what the agent process can touch

The agent runs as the unprivileged user `sandbox`. The sandbox runtime applies the policy's static parts before the agent starts:

- **Landlock** (a Linux security module) limits the filesystem: here `/usr`, `/lib`, `/etc` are read-only, `/sandbox` and `/tmp` are writable, everything else is invisible. OpenShell 0.1 requires Landlock ABI v3, so the node needs Linux 6.2 or newer.
- **seccomp** filters dangerous system calls, and the process cannot regain root.
- These are **static**: fixed when the sandbox is created.

<DeckScene src="openshell" only="kernel" title="Two kernel filters" />

## Kubernetes guardrails

- **Resource admission**: a sandbox may use a cluster resource (a RuntimeClass, a PriorityClass, a volume) only if the operator labelled it `openshell.ai/sandbox-attachable=true`.
- **Kyverno** rejects any sandbox pod that asks for the host's network, PID or IPC namespace.

## Exercise: test the seal from inside

You created `agent-0` and saw it become two pods. The agent lives in the **workload** pod. To poke at it directly you go **into the sandbox**, through the gateway and the supervisor, with an ordinary `exec`.

<Section n="1" title="Confirm it's there" goal="Find the workload pod and its supervisor.">

<Step n="1" title="List the sandbox pods">

```bash
kubectl -n openshell-lab-default get pods -o wide
```
<Output>
<ExpectedOutput>
{`NAME                                                 READY   STATUS    RESTARTS   AGE
agent-0                                              1/1     Running   0          75s
os-supervisor-bb5457b5-93bf-40d1-8421-7ce92d1984cf   1/1     Running   0          75s`}
</ExpectedOutput>
</Output>

`agent-0` is the workload pod; `os-supervisor-…` is its supervisor. Both live in `openshell-lab-default`, the namespace the gateway created for the workspace `default`.

</Step>

</Section>

<Section n="2" title="Get a shell inside" goal="Explore the sandbox from an interactive shell.">

<Step n="1" title="Open the shell">

```bash-interactive
./scripts/fleet shell agent-0
```

</Step>

<Step n="2" title="Try a few things">

That drops you into a shell **inside the sandbox**. Try a few things there:

```bash-ref
id
ls /
touch /usr/x
touch /sandbox/notes.txt && ls /sandbox
```

<Callout type="note" title="Type these, don't Run them">
These only prove anything when typed <em>inside</em> the sandbox prompt. Run from the Cluster shell they'd show you the VM itself. Type <code>exit</code> to come back.
</Callout>

</Step>

</Section>

<Section n="3" title="Or one command at a time" goal="Check the sandbox user and its Landlock filesystem rules.">

<Step n="1" title="Who the agent runs as">

`openshell sandbox exec` runs a single command in the sandbox and returns, safe to Run from here:

```bash
openshell sandbox exec -n agent-0 -- id
```
<Output>
<ExpectedOutput>
{`uid=10001 gid=10001 groups=10001`}
</ExpectedOutput>
</Output>

An unprivileged user (`whoami` has no name for it, and that's fine).

</Step>

<Step n="2" title="The filesystem, enforced by Landlock">

Now the filesystem, enforced by **Landlock**:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'touch /usr/x; touch /sandbox/x && echo "/sandbox is writable"; ls /root'
```
<Output>
<ExpectedOutput>
{`touch: cannot touch '/usr/x': Permission denied
/sandbox is writable
ls: cannot open directory '/root': Permission denied`}
</ExpectedOutput>
</Output>

Exactly the policy's `filesystem_policy`: `/usr`, `/etc`, `/lib` read-only, `/sandbox` and `/tmp` writable, everything else out of reach. Even `ls /` is denied.

</Step>

</Section>

<Section n="4" title="Prove the network seal" goal="Show the agent cannot reach the cluster API, and see what the supervisor prepared.">

<Step n="1" title="Try the Kubernetes API">

The Kubernetes API is one hop away on the cluster network, but not for the agent:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -sk -m 6 -o /dev/null https://kubernetes.default.svc.cluster.local/version || echo "blocked (curl exit $?)"'
```
<Output>
<ExpectedOutput>
{`blocked (curl exit 7)`}
</ExpectedOutput>
</Output>

</Step>

<Step n="2" title="Read the prepared environment">

And look at the environment the supervisor prepared:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'env | grep -E "^(HOME|LITELLM_API_KEY|SSL_CERT_FILE)" | cut -c1-80'
```
<Output>
<ExpectedOutput>
{`HOME=/sandbox
LITELLM_API_KEY=openshell:resolve:env:v3967582269993490644_LITELLM_API_KEY
SSL_CERT_FILE=/run/openshell-supervisor-ca/material/ca-bundle.crt`}
</ExpectedOutput>
</Output>

`LITELLM_API_KEY` is a placeholder (next lessons). `SSL_CERT_FILE` points at a bundle that includes the supervisor's CA: that's how the supervisor can inspect HTTPS requests at L7 while the agent's TLS still validates.

</Step>

</Section>

<Section n="5" title="The Kubernetes side of the seal" goal="See the NetworkPolicy that pairs each workload with its supervisor.">

<Step n="1" title="List the NetworkPolicies">

The isolation between the two pods is ordinary Kubernetes:

```bash
kubectl -n openshell-lab-default get networkpolicy
```
<Output>
<ExpectedOutput>
{`NAME                                              POD-SELECTOR
openshell-sandbox-ssh                             openshell.ai/managed-by=openshell
openshell-sandbox-supervisors                     openshell.ai/boundary-role=supervisor
openshell-sandbox-workloads                       openshell.ai/boundary-role=workload
os-control-593394eb-6dd0-4be8-a33c-e07a89f40f9b   openshell.ai/boundary-pair=593394eb-…
os-control-bb5457b5-93bf-40d1-8421-7ce92d1984cf   openshell.ai/boundary-pair=bb5457b5-…`}
</ExpectedOutput>
</Output>

Workload pods (`boundary-role=workload`) may talk only to their paired supervisor (`boundary-pair`). The supervisor is the one with network access, and it applies the policy.

</Step>

</Section>

<Callout type="lab" title="A sandbox is a pair of pods">
No magic VM: a workload pod with a locked-down process, a supervisor pod that owns its network, and NetworkPolicy between them. Kubernetes gives you scheduling, lifecycle and RBAC; OpenShell adds the isolation and the policy on top.
</Callout>
