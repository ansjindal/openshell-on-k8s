In [Build an agent](/learn/build-an-agent) you created one sandbox by hand and installed pi in it. The lab's default agent, **OpenClaw**, comes preinstalled in the sandbox image, and a small helper, `fleet`, creates as many sandboxes as you ask for with the same `openshell sandbox create`. Here you use it, read the command behind it, and look at what a sandbox is made of on the cluster.

**Concept:** [Topics 4 and 5 in the Overview: gateway and supervisor, and the boundary up close](/learn/openshell#t-4).

<Section n="1" title="The easy way: the fleet helper" goal="Create agent-1 with one helper command.">

<Step n="1" title="Meet the fleet helper">

`./scripts/fleet` is a thin wrapper around the `openshell` CLI and `kubectl` that the next lessons reach for:

```bash-ref
fleet up [N]                          # create sandboxes agent-0 … agent-(N-1)
fleet down                            # delete every fleet sandbox
fleet status                          # sandboxes + the pods behind them
fleet task "<prompt>" [agent-i|all]   # run a prompt across the fleet, in parallel
fleet shell <agent-i>                 # interactive shell inside one sandbox
fleet logs <agent-i>                  # OpenShell logs for one sandbox
```

</Step>

<Section n="2" title="The direct way: the openshell CLI" goal="Read the command fleet up runs for each agent.">

<Step n="1" title="The create command and its flags">

`fleet up` runs this for each agent:

```bash-ref
openshell sandbox create --name agent-1 \
  --provider litellm \
  --policy manifests/policies/baseline.yaml \
  --memory 3Gi \
  --no-tty --detach -- sleep infinity
```

| Flag | What it does |
|---|---|
| `--provider litellm` | attach model access: a placeholder `LITELLM_API_KEY`, plus the provider's policy entry |
| `--policy …baseline.yaml` | start from the lab baseline: deny all network, `/sandbox` and `/tmp` writable |
| `--memory 3Gi` | the workload pod's memory request and limit (one OpenClaw turn peaks near 2 GB). `--cpu` would also become a *request*: on an 8-vCPU VM a few of those fill the node |
| `--detach` and `-- sleep infinity` | the command after `--` is the sandbox's **main process**; the sandbox lives as long as it runs |
| (no `--from`) | the gateway's default image, `ghcr.io/ansjindal/openshell-on-k8s/openclaw-sandbox`: OpenClaw on the OpenShell community base |

Without a trailing command and `--detach`, `openshell sandbox create` opens an interactive shell in the new sandbox instead; type `exit` to leave.

</Step>

</Section>

<Section n="3" title="What happened on the cluster" goal="Trace the gateway's work down to Kubernetes objects.">

<Step n="1" title="List the Sandbox resources">

The CLI never touches Kubernetes. It calls the **gateway**, which:

1. stores the sandbox and its policy (revision 1);
2. writes a `Sandbox` resource in the workspace's namespace, `openshell-lab-default` (the gateway creates one namespace per workspace); the **agent-sandbox controller** turns it into the **workload pod** `agent-1`;
3. starts the **supervisor pod** `os-supervisor-<id>`, which fetches the policy and the provider credentials and becomes the workload's only network path.

```bash
kubectl -n openshell-lab-default get sandboxes
```

<Callout type="note" title="Keep agent-0 around">
The rest of the course, including the console and the Module 4 capstone, assumes <code>agent-0</code> is up. To scale back without tearing everything down: <code>openshell sandbox delete agent-1</code>. <code>fleet down</code> is for when you're done with the launchable.
