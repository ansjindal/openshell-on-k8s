The `litellm` provider was set up for you; you read it in [1.3](/learn/inference). Now build one yourself, for a service the agent should call with a token it never sees, and watch the real token arrive at the other end.

The service is a tiny **echo API** (`manifests/demo-echo/echo.yaml`): it answers every request with the method, path and headers it received. So you can see exactly what leaves the sandbox.

  will="deploy an echo API, write and import a provider profile, attach a provider to agent-0, watch the real token arrive, rotate it and detach it."
  time="about fifteen minutes. Each step has a Run button that runs its command on your lab VM."
/>

<Section n="1" title="Deploy the echo API the provider will call">

First, a service to call: the echo API answers every request with what it received, so you can see exactly what leaves the sandbox.

<Step n="1" title="Apply the echo API's manifest">

Deploy the echo API in its own namespace, `lab-demo`, and wait for it to be ready:

```bash
kubectl apply -f manifests/demo-echo/echo.yaml && kubectl -n lab-demo rollout status deploy/echo --timeout=120s
```


</Step>

</Section>

<Section n="2" title="Write a provider profile for the echo API">

A profile is the access contract for a credential: which variable a sandbox gets, where the credential may go, and for which requests.

<Step n="1" title="Read the profile, field by field">

A **provider profile** is the contract for one kind of credential. Read `manifests/demo-echo/echo-api.profile.yaml`:

```bash
cat manifests/demo-echo/echo-api.profile.yaml
```

The parts that matter:

```bash-ref
credentials:
  - name: token
    env_vars: [ECHO_TOKEN]          # what the sandbox gets (as a placeholder)
    auth_style: bearer              # how the supervisor sends the real value
    header_name: authorization
endpoints:
  - host: echo.lab-demo.svc.cluster.local   # the ONLY place the token may go (FQDN)
    port: 8080
    protocol: rest
    enforcement: enforce
    rules:
      - allow: {method: GET, path: "/api/**"}   # and only for these requests
```

</Step>

<Step n="2" title="Lint the profile and import it into the gateway">

Check the profile against the schema, then import it into the gateway, where every workspace can use it:

```bash
openshell profile lint -f manifests/demo-echo/echo-api.profile.yaml && openshell profile import -f manifests/demo-echo/echo-api.profile.yaml
```
<Output>
<ExpectedOutput>
{`Provider profile lint passed.
Imported 1 provider profile.`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="3" title="Create a provider from the profile">

Hand the real token to the gateway, which stores it. The sandbox will never see it.

<Step n="1" title="Create it, with the token read from the environment">

A **provider** is an instance of a profile holding a real credential. Pass the value through the environment, so it never appears in your shell history or the process list:

```bash
ECHO_TOKEN=lab-secret-123 openshell provider create --name echo --type echo-api --credential ECHO_TOKEN
```
<Output>
<ExpectedOutput>
{`✓ Created provider echo`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="4" title="Attach the provider to agent-0 while it runs">

Attach the provider to `agent-0` while it runs: it gets a placeholder variable and the profile's rule, with no restart.

<Step n="1" title="Attach the echo provider">

Attach the `echo` provider to `agent-0` while it runs; `--wait` returns once the supervisor has the new policy:

```bash
openshell sandbox provider attach agent-0 echo --wait
```
<Output>
<ExpectedOutput>
{`agent-0 / echo: ready (unspecified)
  Installed: credentials=true, policy=true, future process environment=true
  Wait: complete`}
</ExpectedOutput>
</Output>

No restart: the sandbox applied the new credential and the profile's policy.

</Step>

<Step n="2" title="Check the placeholder the sandbox got">

New processes in the sandbox see a new variable, `ECHO_TOKEN`. Print it:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'echo $ECHO_TOKEN'
```
<Output>
<ExpectedOutput>
{`openshell:resolve:env:v2062283290838615716_ECHO_TOKEN`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="5" title="Call the echo API from the sandbox">

Call the echo API from inside the sandbox and see what arrives: the real token, but only on requests the profile allows.

<Step n="1" title="A GET carries the real token">

Call the echo API with the placeholder in `Authorization`. The echo shows what really arrived:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -H "Authorization: Bearer $ECHO_TOKEN" http://echo.lab-demo.svc.cluster.local:8080/api/whoami' | grep -E '"path"|authorization'
```
<Output>
<ExpectedOutput>
{`  "path": "/api/whoami",
    "authorization": "Bearer lab-secret-123"`}
</ExpectedOutput>
</Output>

The agent sent the placeholder; the echo service received `lab-secret-123`. The supervisor swapped it on the way, because the request matched the profile's endpoint and rule.

</Step>

<Step n="2" title="A POST never leaves">

The profile allows `GET` only. Send a `POST` with the same placeholder:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -o /dev/null -w "HTTP %{http_code}\n" -X POST -H "Authorization: Bearer $ECHO_TOKEN" http://echo.lab-demo.svc.cluster.local:8080/api/x'
```
<Output>
<ExpectedOutput>
{`HTTP 403`}
</ExpectedOutput>
</Output>

</Step>

</Section>

<Section n="6" title="Rotate the token without touching the sandbox">

Change the token in the gateway, and the sandbox uses the new one on its next request, with nothing to restart.

<Step n="1" title="Update the provider's token">

Change the credential in the gateway; every sandbox with the provider attached picks it up, still without a restart:

```bash
ECHO_TOKEN=lab-secret-456 openshell provider update echo --credential ECHO_TOKEN --wait
```


</Step>

<Step n="2" title="See the new value arrive">

Call the echo API again. Nothing in the sandbox changed:

```bash
openshell sandbox exec -n agent-0 -- sh -c 'curl -s -H "Authorization: Bearer $ECHO_TOKEN" http://echo.lab-demo.svc.cluster.local:8080/api/whoami' | grep authorization
```
<Output>
<ExpectedOutput>
{`    "authorization": "Bearer lab-secret-456"`}
</ExpectedOutput>
</Output>

The agent's placeholder didn't change; only the value behind it did.

</Step>

</Section>

<Section n="7" title="Detach the provider again">

Detach the provider: the placeholder and its rule disappear from the sandbox.

<Step n="1" title="Detach echo from agent-0">

Detaching revokes both the credential and the policy entry the profile added:

```bash
openshell sandbox provider detach agent-0 echo --wait
```


</Step>

</Section>

<Callout type="nv" title="Why this matters">
An agent with a token in its environment can send it anywhere: in a URL, a log line, a prompt-injected request to an attacker. With a provider, the token is only ever materialised by the supervisor, on requests that match the profile's endpoint and rules, and the agent can't read it back. Rotation and revocation are one command, for every sandbox at once.
</Callout>

## What you learned

<Learned next="/learn/workspace" nextLabel="Give it a soul: workspace files">

- **A provider is a credential plus its contract.** The profile says which variable a sandbox gets, where the credential may go and for which requests; the gateway keeps the real value.
- **Attach and detach live.** The sandbox gets a placeholder and the profile's rule without a restart, and loses both when you detach.
- **Only allowed requests carry the real token.** A GET reached the echo API with it; a POST never left the sandbox.
- **Rotation is one command.** Update the provider, and the next request uses the new token.

</Learned>
